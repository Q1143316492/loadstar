## 需求，与已经踩到的坑

最初的需求是「一个能辅助我理解陌生代码库的技能」：给定一个陌生库，产出帮人读懂它的文档，机械活交给脚本、判断留给模型。
做完五代产物（自研地图格式 / 散文 wiki / 符号索引 / 结构化文档集 / 路线版 / 结构契约）——62 个文件、133 个测试、
353 行机械关卡——判定**不成立**。原因不在形式上：**这类文档没有判据**。关卡能查「锚点存不存在、索引一致不一致、
行数超没超」，查不了「内容对不对、值不值得看」；于是每一轮改进都落在形式上，而真正的判据是「这对我有没有用」——
两者永远对不上。最终的评价是：**产出的文档质量，和我直接跟 AI 聊一轮差不多**。

## 三条判据：一个技能要成立，须同时满足

| 判据 | 含义 | 上面的反证 |
|---|---|---|
| **① 意图由人给定** | 需求 / issue / 不变量 / 规范 | 代码里读不出「什么重要」：EqZero 的 GAS 流程写到第 8 步就断在蓝图里 |
| **② 输出可被打脸** | 跑测试 / 复现 / 对照代码 | v4 的关卡只能查结构，内容写错了也无法判定 |
| **③ 范围有界** | 一个 diff / 一个模块 | 全库无法定义「做完了」与「漏了什么」 |

**② 尤其重要**：它是判断一个技能是否只是空操作的唯一方式。没有它，你分不清「技能起作用了」和「技能什么都没做」。

## 关键语句（取自上游，逐条附出处）

| 语句 | 出处 | 对本仓的作用 |
|---|---|---|
| **空操作判据**：模型默认就会照做的指令，等于白花上下文。测法：**把它删掉，行为会不会变？** 不会变就别写 | `writing-for-agents` | 解释 codeview 为什么失败——技能的核心动作正是模型的默认动作；改外壳（地图/索引/文档集/路线）改变不了默认，所以产出约等于直接聊 |
| **刻意偏离**：刻意偏离显而易见路径的做法要记下来，否则下一个人会来「修正」某个本来就是刻意的东西 | `ADR-FORMAT.md` | 本仓为什么保留「已否决的」清单 |
| **建检查 > 写规则**：机械性违规配确定性检查，`CODING_STANDARDS.md` 只留给真正的判断题 | `retro` | 四层模型的来源：能用检查兜住的，不要写成措辞 |
| **先读再断言**：在说某个技能做什么、或建议跳过某一步之前，先读那个技能的 `SKILL.md`；摘要只用于定位方向 | `ask-matt` | 本 README 把「已失败的东西」放在最前面的原因 |
| **YAGNI 划范围**：没人改的代码里的重构机会，永远收不回成本；先用 `git log` 找热点 | `improve-codebase-architecture` | 它跑 EqZero 能筛出真问题的原因（也就是「失控库评审」的可行性来源） |

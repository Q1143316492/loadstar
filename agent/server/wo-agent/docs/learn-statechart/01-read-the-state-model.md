# 01 · 把代码读成一张状态表

**产物**：一张「事件 × 当前状态 → 新状态」的表，以及标出你不确信的格子。
**认领**：为验收 1 做准备。
**预计**：40 分钟。

## 读什么

[`src/session/session.py`](../../src/session/session.py) 里的 `fold_surface`，从函数定义读到 `return nodes`。

先把这三件事找出来：

1. **状态是什么**——函数里有哪些变量，它们在循环里怎么变。答案是 `nodes`：一个 `(seq, message)` 的列表。
2. **事件是什么**——循环每一项是什么。答案是 `SessionEvent`，它带一个 `seq`、一个 `time`、一个 `event`。
3. **哪一步让状态变**——对每种事件，`nodes` 怎么被改。

读的时候不要管 `derive_event_message` 内部做了什么——它只决定「这条事件上不上表层」，把它当成一个黑盒，`None` 就是「不上」。

## 这张表（已填好）

| 事件 | `nodes` 怎么变 |
|---|---|
| 投影结果是 `None` | **什么都不做**。事件留在日志里，但不进表层。 |
| `surface_op == "append"` | 尾部追加 `(entry.seq, msg)`。表层变长一格。 |
| `replace` 且 `start`/`end` 都在表层 | 把表层里 `start` 位置到 `end` 位置这一段**整段换成一个节点** `(entry.seq, msg)`。表层可能一下子短好几格。 |
| `replace` 但 `start` 或 `end` 不在表层 | **报错 A**：`start seq ... or end seq ... not found in surface`。 |
| `replace` 但 `start` 的表层位置晚于 `end` | **报错 B**：`start seq ... is after end seq ...`。注意比较的是**表层位置**，不是 seq 数值。 |
| `source_event_seqs` 非空，但漏了被遮蔽的节点 | **报错 C**：`must include every shadowed surface node; missing ...` |
| `source_event_seqs` 里出现 ≥ 当前事件 seq 的值 | **报错 D**：`must reference earlier events: ... >= ...` |

（另外还有一种：`surface_op` 既不是 `"append"` 也不是 `SurfaceReplace` → 报错 `unknown surface_op`。实际代码走不到，属于防御。）

## 三问的答案

**一、为什么 `start`/`end` 是 seq，而不是下标？**

因为一次 `replace` 之后，表层的**顺序**就不再等于 seq 的**大小**。表层是「现在给人看的顺序」，seq 是「事件在日志里的出生位置」——两者会分叉。

一个具体的例子：

```text
初始：append 四次        → 日志 seq 0,1,2,3；表层 [0, 1, 2, 3]
第一步：replace(1, 2)    → 新事件 seq 4；表层 [0, 4, 3]
第二步：replace(3, 4)    → 数值上 3 < 4 完全正常，但表层里 3 排在 4 后面 → 报错 B
```

如果按数值区间算，第二步没有任何问题；按表层位置算，它反了。**`SurfaceReplace` 的 docstring 警告的就是这件事。**

**二、被替换掉的节点去哪了？**

还在 `events` 日志里，只是不再参与投影。所以「日志是事实源、表层是投影」——`derive_messages()` 每次都是从日志重新折一遍，不是增量改一份消息数组。审计、重放、分叉都因此免费。

**三、四种错里，哪些是「调用方写错」，哪些是「数据自相矛盾」？**

- **A（找不到节点）和 B（位置反了）**：调用方把位置说错了。报错可以直接告诉它错在哪。
- **C（漏了被遮蔽的节点）和 D（引用了未来事件）**：事件**自己携带的溯源信息**与日志的实际内容对不上。D 尤其严重——它意味着这条事件声称的因果顺序是倒置的，日志不再可信。

这个区分在第 04 篇会变成建模选择：A、B 是「参数校验」，C、D 是「日志完整性不变量」。

## 你不确信的格子

表里一定有某一格你不确定。**把它圈出来**，不要猜。第 04 篇写规格时，那一格会变成模型里最需要小心的地方。

如果你一格都不确定，说明读得太快——回到代码里，对最复杂的那行 `nodes[start_idx : end_idx + 1] = [(entry.seq, msg)]` 问：如果 `start_idx` 和 `end_idx` 指向的是表层的两端，中间可能夹着什么？

## 自检

不用再填表了。拿这三问对自己：

1. 一个 `replace(3, 4)`，为什么在表层 `[0, 4, 3]` 上是错的，而在表层 `[0, 3, 4]` 上是对的？
2. 被 `replace` 遮蔽的节点还能被重新放回表层吗？
3. C 和 D 两种错，哪一种会让整份日志失去可信度？

# 02 · 手写一个属性测试

**产物**：一段能跑的脚本，随机生成事件序列、每步检查规则，第一次跑绿。
**认领**：为验收 2 做准备。
**预计**：1 小时。

## 要建立的两个观念

**一、测试只走一条路，你要的是走很多条。**

平时写的测试是「给输入 X，断言输出 Y」。属性测试换个问法：「**无论**你给什么输入，这几条规则都成立吗？」然后用随机输入去撞。

**二、规则不是「结果对不对」，是「任何时刻都不该出现的东西」。**

「登录成功返回 200」是结果。「表层里不会有同一个节点出现两次」是规则——它在**每一步之后**都该成立，和具体哪一步无关。

## 先跑起来

示例脚本在 [`examples/prop_fold.py`](examples/prop_fold.py)。先原样跑一遍：

```sh
PYTHONIOENCODING=utf-8 .venv/Scripts/python docs/learn-statechart/examples/prop_fold.py
```

你现在应该看到 `共 2000 轮，违反 0 次`。

**但是这个绿灯是假的**——`check()` 现在永远返回 `None`，什么都没检查。这也是属性测试最容易骗过自己的地方：**一个从不失败的检查，和一个不存在的检查，长得一模一样。**

## 你的任务

填 `check()`。它收到两个参数：`surface_seqs`（折叠出来的表层 seq 列表）和 `events`（完整事件列表）。

写三条，每条返回一句人话的违反说明，或 `None`：

1. 表层里没有重复的 seq。
2. 表层里的每个 seq 都小于事件总数。
3. `replace(s, e)` 之后，`s` 和 `e` 都不再留在表层。这条要拿到事件里的 `surface_op`。

第 3 条有个陷阱，脚本注释里写了：**不要**写成「[s, e] 区间里的 seq 都消失」。`replace` 之后表层顺序可以不再等于 seq 顺序，数值落在区间里的节点可能本来就不在 `s..e` 之间——那样写会误报一堆。

## 撞墙是正常的

填完再跑。可能出现的三种情况：

- **0 次违反**：恭喜，说明这三条规则在现有实现上成立。**但这才刚刚开始**——第 03 篇会让你亲眼看到它失败。
- **出现违反**：先别改代码。读一下打印出来的事件序列和表层。你有三种可能：规则写错了、随机生成器生成了代码根本不该接受的事件、或者代码真有 bug。判断顺序是**从「我错了」开始**，最后才怀疑代码。
- **脚本崩了**：`check()` 里访问了不存在的属性。把 `events` 里元素打印出来看看它是什么类型。

## 让你的随机序列更狠一点

现在的生成器只会在已有事件里挑 seq。试试这两个改动，各跑一次：

1. **提高 replace 的比例**（`0.3` 改成 `0.5`），看违反数变不变。
2. **让 replace 连续发生**——在 `gen_events` 里，如果上一条是 replace，就更可能再来一条。理由是：连续 replace 才会让「表层顺序 ≠ seq 顺序」真正发生，而那正是这个对象最有趣的地方。

## 关于固定种子

`main(seed=0)` 里的种子是固定的，所以每次跑出的序列一样。这是刻意的：**失败必须能重放**。当你看到一条违反时，记下轮次，把种子固定住，它下次还会出现。

这也解释了为什么失败报告要打印完整的事件序列——那是你的「最短反例」的雏形。第 05 篇会用工具给你真正最短的那条。

## 做完的标志

- 三条规则填完，脚本能跑。
- 你能说出为什么这里的「跑绿」不等于「代码是对的」。
- 你试过提高 replace 比例，并且观察到了结果的变化（或没变）。

第 03 篇：故意把代码改坏，看这三条规则能不能抓住它。

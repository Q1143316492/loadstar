「状态」不是函数参数，是五个变量的快照

下面是刚才真实跑出来的东西。63 个状态不是凑的，是从初始状态一步一步走出去的。

01一个状态长什么样

这是初始状态。五个变量，每个都只是一个值。

State 0 · 程序刚启动
nextTurn[] ← 空队列
nextStep[] ← 空队列
claimed{} ← 还没认领过任何东西
pushed{} ← 还没推过任何东西
nextId0 ← 下一个消息编号

注意那个标「幽灵」的变量。pushed 在 inbox.py 里根本不存在。它有，只是因为规则「消息不会丢」需要拿「曾经有什么」和「现在有什么」对比。代码里没有这个变量，就没法检查这条规则。

这就是建模时最常做的一件事：为了写出规则，往模型里加代码里没有的变量。

02从它出发，一步能走到哪

实际枚举出的三个后继。注意第三个 —— 它走回了自己。

  • State 0  ·  NT=[] NS=[] C={} P={}
    PushTurnNT=[0]  NS=[]  C={}  P={0}
    PushStepNT=[]  NS=[0]  C={}  P={0}
    ClaimStepNT=[]  NS=[]  C={}  P={}  ← 和上面一模一样
    ClaimStep 没有新状态。队列本来就是空的，claim 完还是空的。所以它不算「新的状态」——这就是去重，也是深度 1 只有 2 个状态而不是 3 个的原因。

这就是「状态」和「操作」的区别。操作可以有很多次，状态只有有限多个。枚举器只关心走到了哪些不同的状态，走两次同样的状态没有意义。

中间涨得快、两头小，是因为队列长度有上限 2。到了深度 6 只剩 2 个状态还能往外走 —— 说明探索到头了。

04为什么「状态数」会失控

因为状态是变量取值的乘积，不是和。

nextTurn长度 0–2 的编号序列×?
nextStep长度 0–2 的编号序列×?
claimed已认领编号的集合×2ⁿ
pushed推过的编号集合×2ⁿ
nextId0–4（被 CONSTRAINT 截断）×5

现在是 63，因为队列上限是 2、id 上限是 4。把上限从 2 改到 3，或者加一个「取消过」的集合，数字立刻翻几倍。这就是状态爆炸——它不是你跑得慢，是组合数本身涨得快。

所以真正的技能是：砍掉不影响结论的变量。消息内容砍掉、时间戳砍掉、协程砍掉。留下的每一个变量，都得是「规则要读它」或者「操作会改它」。

1 ∈ pushed，但 1 ∉ claimed ∪ NT ∪ NS。 它被推进来过，现在哪都不在。
这一条检查就是一行： pushed ⊆ claimed ∪ nextTurn ∪ nextStep

06所以「扩展到复杂系统」是什么意思

不是把整个系统塞进去，是挑一个小到能穷举、又真到能出错的切片。

系统建模的那一片不建模
Inbox
（我们做的）		 两个队列 + 已认领 + 推送过 消息内容、协程、cancel
S3 / DynamoDB
（AWS 公开的案例）		 三五个节点、复制消息、选主 网络栈、磁盘格式、用户数据
你的 wo-agent
（下一个候选）		 会话压缩事务：start → summary → replace → end LLM 调用、流式分片、工具执行

共同点：建模的那一片，都是「几个变量 + 一串有顺序的操作」。不管系统多大，被建模的那一块都只有这么点东西。剩下的都是它周围的噪音。

你现在能回答这个问题吗：换一个新对象，你会挑哪几个变量？

挑变量的判据只有两条 —— ① 规则要读它；② 操作会改它。两条都不满足的，就是噪音，砍掉。

## 问题

属性测试工具（hypothesis）能不能进 wo-agent 的 dev 依赖？

背景事实：仓库当前没有 hypothesis（未安装、无属性测试先例）；`CLAUDE.md` 的定位是「可控规模的 Python 内核 + 极窄宿主」，测试约定是「每个模块自带 tests/，不依赖网络与真实 key」。

要权衡的：

- 选项 A：加 `hypothesis` 到 dev extras。好处是教程里的属性测试能直接跑；代价是往一个刻意保持窄的仓库里加了一个通用测试框架。
- 选项 B：不加，教程里的属性测试用**手写随机序列**（`random.Random(seed)` 固定种子）实现。好处是不动仓库依赖；代价是收缩与反例最小化要自己写几十行。
- 选项 C：教程阶段先 B，若第二、三次使用仍觉得手写不值得，再开一张票改 A。

答案产出：选哪个、理由、以及如果选 B，那段手写代码放在哪（教程目录还是 `src/*/tests/`）。

类型：grilling
状态：已解决
阻塞于：无

## 答案

**选 C：教程阶段先手写，不改仓库依赖。**（按推荐落定，未经你确认。）

理由：`hypothesis` 是个通用测试框架，一旦进来就会成为仓库的既有范式，而这次学习的目的只是让你体会「随机走状态 + 每步检查不变量」，不是给仓库铺测试基建。手写版本大约四十行——随机序列生成、固定种子、失败时打印路径——这四十行本身也是教学内容，你能看见反例是怎么被记下来的。

**代码落点**：`docs/learn-statechart/` 下的示例目录，不进 `src/*/tests/`。原因同上：在仓库还没有明确测试范式之前，不要用教程代码去定义它。

**何时改判**：如果你在第二个对象、或第三个场景里仍然要重写这四十行，那就说明它不是一次性的，届时开一张新票把它换成 `hypothesis`，并单独立项评估依赖边界。

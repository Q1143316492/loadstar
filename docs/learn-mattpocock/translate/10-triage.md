### 10.1 Triage（Triage）

让项目 issue tracker 上的 issue 走过一个小型的状态机，由 triage 角色构成。

如果这个仓库把外部 pull request 当作一个请求入口面（见 issue-tracker 配置），triage 也覆盖它们：**一个 PR 就是带着代码的 issue**，用同样的角色、同样的状态、同样的状态机，只有下面几处标着「for a PR」的差异。按 tracker 配置把裸 `#42` 解析成一个 issue 或 PR。

triage 期间发布到 issue tracker 的每条评论或 issue，都**必须**以这条免责声明开头：

```
> *This was generated by AI during triage.*
```

### 10.3 角色（Roles）

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完整指定，可供 AFK agent 接手
- `ready-for-human`：需要人类来实现
- `wontfix`：不会被处理

对一个 PR，同样的状态是针对所附代码来读的：`ready-for-agent` 意味着已附上一份 brief，agent 应当对这份 diff 走下一步；`ready-for-human` 意味着它已可供人类合并。

每个已 triage 的 issue 都应当恰好带一个类别角色和一个状态角色。如果状态角色冲突，先把它标出来并询问维护者，再做任何别的事。

这些是规范的角色名。issue tracker 中实际使用的标签字符串可能不同。这个映射应该已经提供给你了。如果没有，告诉用户去运行 `/setup-matt-pocock-skills`。

状态迁移：一个无标签的 issue 通常先到 `needs-triage`；从那里它移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 回到 `needs-triage`。维护者随时可以覆盖；把看起来异常的迁移标出来并在继续之前先问。

### 10.4 调用（Invocation）

维护者调用 `/triage` 并用自然语言描述他们想要什么。解释这个请求并行动。例如：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

### 10.5 展示需要注意的东西（Show what needs attention）

查询 issue tracker 并呈现三个桶，最旧的在前：

1. **Unlabeled**：从未 triage 过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次 triage 笔记以来报告者有活动**：需要重新评估。

当 PR 在范围内时，把这些外部 PR 也放进这些桶，并给每一行打上 `[PR]` 或 `[issue]` 标记。发现过程只呈现*外部* PR（谁算外部由 tracker 配置定义），所以协作者正在进行的 PR 不是 triage 工作。这个过滤器只用于发现；一个被明确点名的 PR 无论作者是谁都总是会被 triage。

展示数量以及每条一行摘要。让维护者挑选。

### 10.6 Triage 一个具体的 issue 或 PR（Triage a specific issue or PR）

1. **收集上下文。**完整阅读该 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析任何先前的 triage 笔记，免得你重复询问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的 ADR。对代码库跑两项检查：(a) **冗余**：按领域概念（而不只是请求的措辞）搜索所请求行为的已有实现，并报告你查过哪里。如果找到了，那就是一个已实现的 `wontfix`（第 5 步）。(b) **先前否决**：读 `.out-of-scope/*.md`，把任何与这个请求相似的都翻出来。

2. **给出建议。**把你的类别和状态建议连同理由告诉维护者，再加上一段与该请求相关的简要代码库摘要（包括它是否已经实现）。等待指示。

3. **验证主张。**在任何拷问之前，先检查该主张站得住脚。对 bug，按报告者的步骤复现它。对 PR，确认 diff 做了它所声称的事：检出它，运行相关测试或命令。报告发生了什么：已确认（附带代码路径）、失败，还是细节不足（一个强烈的 `needs-info` 信号）。一次已确认的验证会造就强得多的 agent brief。

4. **拷问（如果需要）。**如果请求需要充实，调用 Skill 工具两次，参数分别是 "grilling" 和 "domain-modeling"，一轮问题一轮问题地把它拷问成形，磨锐领域术语，并在决策落定时就地更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发一条 agent brief 评论（[AGENT-BRIEF.md](../../../reference/mattpocock-skills/skills/engineering/triage/AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent brief 相同，但注明为什么它不能被委派（判断取舍、外部访问、设计决策、手工测试）。
   - `needs-info`：发 triage 笔记（模板见下）。
   - 对 `wontfix`，关闭该 issue，评论取决于*为什么*：
     - **已经实现**：这个改动已经存在于代码库中。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给*被否决*的请求用的，不是给已建成的）。
     - **否决（bug）**：给出礼貌的解释，然后关闭。
     - **否决（enhancement）**：写入 `.out-of-scope/`，从评论链接过去，然后关闭（[OUT-OF-SCOPE.md](../../../reference/mattpocock-skills/skills/engineering/triage/OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如果有部分进展，可选地留一条评论。

### 10.7 快速状态覆盖（Quick state override）

如果维护者说 "move #42 to ready-for-agent"，就信任他们，直接应用该角色。确认你将要做什么（角色变更、评论、关闭），然后行动。跳过拷问。如果在没有拷问会话的情况下要移到 `ready-for-agent`，问一下他们是否想写一份 agent brief。

### 10.8 Needs-info 模板（Needs-info template）

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间解决的一切都归到 "established so far" 之下，这样工作不会丢失。问题必须具体且可执行，而不是「请提供更多信息」。

### 10.9 恢复先前的会话（Resuming a previous session）

如果该 issue 或 PR 上存在先前的 triage 笔记，读它们，检查报告者是否回答了任何悬而未决的问题，并在继续之前呈现一幅更新后的图景。不要重复询问已解决的问题。

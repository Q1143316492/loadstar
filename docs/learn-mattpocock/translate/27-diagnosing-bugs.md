### 27.1 诊断 bug（Diagnosing Bugs）

一套针对难缠 bug 的纪律。只有明确有理由时才跳过阶段。

探索代码库时，读 `GLOSSARY.md`（如果存在）以对相关模块建立清晰的心智模型，并检查你正在触碰区域的 ADR。

#### 27.1.1 脱敏（Redact）

本技能会让你展示命令、输出和捕获的产物。**先对每一个秘密脱敏**：在原处写 `<REDACTED>`。针对环境变量构建回路，让凭据留在环境里，而不是留在你展示的东西里。捕获的产物带有认证头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断这个 bug，就说出来并询问用户。

#### 27.1.2 阶段 1：建立反馈回路（Phase 1: Build a feedback loop）

**这就是本技能的核心。** 其他一切都是机械活。如果你为这个 bug 拿到一个**紧的**通过/失败信号，即一条紧反馈回路（`tight feedback loop`）（一个会在 _这个_ bug 上变红的信号），你就能找到原因；二分、假设检验和插桩都只是在消费它。如果你没有，再怎么盯着代码看也救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

##### 27.1.2.1 构建回路的方式，大致按这个顺序（Ways to construct one, in roughly this order）

1. **失败的测试**，放在任何能触达这个 bug 的接缝上：单元、集成、e2e。
2. **针对运行中的开发服务器的 curl / HTTP 脚本。**
3. **带 fixture 输入的 CLI 调用**，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/控制台/网络做断言。
5. **重放一条捕获的轨迹。** 把一个真实的网络请求 / 载荷 / 事件日志存到磁盘；在隔离环境中让它重走那条代码路径。
6. **一次性（`throwaway`）脚手架。** 拉起系统的一个最小子集（一个服务、mock 掉的依赖），用一次函数调用就能跑过 bug 的代码路径。
7. **属性 / 模糊测试回路。** 如果 bug 是「有时输出是错的」，跑 1000 个随机输入，寻找那个失败模式。
8. **二分脚手架。** 如果 bug 出现在两个已知状态之间（提交、数据集、版本），把「在状态 X 启动、检查、重复」自动化，这样你就能用 `git bisect run` 跑它。
9. **差分回路。** 把同一个输入分别跑过旧版本与新版本（或两套配置），diff 输出。
10. **人机协同（`HITL`） bash 脚本。** 最后手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 驱动 _他们_，让回路仍然有结构。捕获的输出回传给你。

建起正确的反馈回路，bug 就修好了 90%。

##### 27.1.2.2 收紧回路（Tighten the loop）

把回路当成一个产品。一旦你有了 _一条_ 回路，就**收紧**它：

- 我能让它更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 我能让信号更锋利吗？（断言具体症状，而不是「没崩」。）
- 我能让它更确定吗？（固定时间、给 RNG 播种、隔离文件系统、冻结网络。）

一条 30 秒的不稳定回路比没有回路好不了多少；一条 2 秒的确定性回路才是紧的，是调试的超能力。

##### 27.1.2.3 非确定性 bug（Non-deterministic bugs）

目标不是干净的复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。50% 概率抖动的 bug 可调试；1% 的不行，所以要不断提高比率，直到它可调试。

##### 27.1.2.4 当你确实无法建立回路时（When you genuinely cannot build a loop）

停下来并明确说出来。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权限，(b) 一份脱敏后的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩（`instrument`）的许可。**不要**在没有回路的情况下提出假设（`hypothesise`）。

##### 27.1.2.5 完成判据：一条会变红的紧回路（Completion criterion: a tight loop that goes red）

阶段 1 在回路**紧**且**能变红（`red-capable`）**时完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），它**已经被你至少运行过一次**（展示该调用及其输出，已脱敏），并且满足：

- [ ] **能变红**：它驱动真正的 bug 代码路径，并断言**用户的确切症状**，所以它能在这个 bug 上变红、修好后变绿。不是「跑起来不报错」；它必须能够 _抓住这个具体的 bug_。
- [ ] **确定性**：每次运行结论相同（不稳定的 bug：按上文所述固定一个高复现率）。
- [ ] **快**：以秒计，不是以分钟计。
- [ ] **agent 可运行**：你能无人值守地运行它；人只在 `scripts/hitl-loop.template.sh` 这条路径上进入环中。

如果你发现自己在命令存在之前就去读代码建理论，**停下：直接跳到假设正是本技能要防止的那个失败。** 没有能变红的命令，就没有阶段 2。

#### 27.1.3 阶段 2：复现 + 最小化（Phase 2: Reproduce + minimise）

运行回路。看着它在 bug 出现时变红。

确认：

- [ ] 回路产生的失败模式是 **用户** 描述的那个，而不是恰好邻近的另一种失败。错的 bug = 错的修复。
- [ ] 这个失败在多次运行间可复现（或者，对于非确定性 bug，复现率足够高，可以据此调试）。
- [ ] 你已经捕获了确切的症状（错误消息、错误输出、慢的耗时），让后面的阶段能验证修复确实处理了它。

##### 27.1.3.1 最小化（Minimise）

一旦它变红，就把复现缩到**仍然会变红的最小场景**。**一次只砍一样**地砍掉输入、调用方、配置、数据和步骤，每砍一刀后重跑回路，只留下对失败承重的东西。

为什么要费这个劲：最小复现会在阶段 3 缩小假设空间（剩下可疑的活动部件更少），并在阶段 5 变成干净的回归测试（`regression test`）。

当**剩下的每一个元素都承重**时完成：去掉其中任何一个，回路都会变绿。

在你既复现了**又**最小化了之前，不要继续。

#### 27.1.4 阶段 3：提出假设（Phase 3: Hypothesise）

在检验任何一个之前，先产生 **3–5 个排好序的假设**。只产生一个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式：「如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。」

如果你说不出预测，这个假设就是一种感觉：丢掉它或打磨它。

**在检验之前把排好序的列表给用户看。** 他们常常有能瞬间重排的领域知识（「我们刚给 #3 部署了一个改动」），或者知道他们已经排除掉的假设。便宜的检查点，巨大的时间节省。不要卡在这里等；如果用户不在，就按你的排序继续。

#### 27.1.5 阶段 4：插桩（Phase 4: Instrument）

每个探针都必须映射到阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定点日志**，放在能区分各假设的边界处。
3. 永远不要「把所有东西都打日志再 grep」。

**给每条调试日志打标签**，用一个唯一前缀，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没打标签的日志会活下来；打了标签的日志会死掉。

**性能分支。** 对于性能回归，日志通常是错的。改为：先建立基线测量（计时脚手架、`performance.now()`、剖析器、查询计划），然后二分。先测量，后修复。

#### 27.1.6 阶段 5：修复 + 回归测试（Phase 5: Fix + regression test）

在**修复之前**写回归测试，但前提是存在一个**正确的接缝**。

正确的接缝是测试能在调用点按实际发生的样子跑过**真实 bug 模式**的地方。如果唯一可用的接缝太浅（bug 需要多个调用方时却只做单调用方测试，或者单元测试无法复刻触发 bug 的那条链），在那里的回归测试只会给出虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 记下它。代码库架构正在阻止这个 bug 被锁死。为下一阶段标出这一点。

如果存在正确的接缝：

1. 把最小化的复现变成该接缝处一个失败的测试。
2. 看着它失败。如果你是靠改动代码或 fixture 才把它逼红的，先拿一份原始副本 `diff` 一下，证明那处改动确实生效了，然后才信任这个结果。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化的）场景重跑阶段 1 的反馈回路。

#### 27.1.7 阶段 6：清理（Phase 6: Cleanup）

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者接缝的缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩都已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 最终证明正确的那个假设写在提交 / PR 消息里，让下一个调试者能学到

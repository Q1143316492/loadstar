### 30.1 逻辑原型（Logic Prototype）

一个单一、自包含的 HTML 文件（一个**可分享的演示**），让任何人通过点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转换或数据形状**时使用这个：这类东西在纸面上看起来合理，但只有把它推过真实情形才会感觉不对。

因为它是一个文件、无需安装任何东西，你可以把它交给非开发者（设计师、PM、领域专家），让他们自己感受这个模型。所以它说的是他们的语言，而不是代码的语言。

#### 30.1.1 何时这是正确的形态（When this is the right shape）

- 「我不确定这个状态机是否处理了先 X 后 Y 的边界情况。」
- 「这个数据模型真的能让我表示……的情形吗？」
- 「我想在写之前摸摸这个 API 应该长什么样。」
- 任何有人想要**按按钮并看着状态变化**的地方。

如果问题是「它应该长什么样」，这就是错的分支。用 [UI.md](../../../reference/mattpocock-skills/skills/engineering/prototype/UI.md)。

#### 30.1.2 流程（Process）

##### 30.1.2.1 陈述问题（State the question）

写代码之前，写下你在做原型的是什么状态模型、什么问题。一段话，放在演示的顶部（放在可见的引言里，不只是一条注释）。回答错问题的逻辑原型是纯粹的浪费，所以把问题明确写出来，以便之后可以核对，无论用户是现在正看着，还是离开（AFK）之后回来查看。

##### 30.1.2.2 把逻辑隔离在一个可移植的模块里（Isolate the logic in a portable module）

把真正的逻辑（回答问题的那个部分）放在一个 `<script>` 块里，写成一个小而纯的模块，以后可以整块取出、放进真实代码库。围绕它的页面是一次性的；这个模块不是。

正确的形状取决于问题：

- **一个纯 reducer**：`(state, action) => state`。当动作是离散事件、状态是单一值时很好。
- **一个状态机**：显式的状态与转换。当「现在到底哪些动作是合法的」是问题的一部分时很好。
- **一小组纯函数**，作用于一个简单数据类型。当没有隐含的当前状态、只有变换时很好。
- **一个具有清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时。

选最契合所问问题的形状，*而不是* 最容易接到页面上的形状。保持它纯净：没有 DOM、没有 `document`、没有伸进它内部的按钮处理器。页面调用它；没有任何东西往反方向流。这正是让原型在自己生命周期结束后仍然有用的原因：问题一旦被回答，被验证的 reducer / 状态机 / 函数集就自己升进真实模块。

##### 30.1.2.3 构建可分享的 HTML 文件（Build the shareable HTML file）

一个文件，纯 HTML/CSS/JS：没有框架、没有打包器、没有服务器，所有东西内联，这样双击就能打开，并且经得起被邮件传来传去。任何人打开它都应该能运行它。

为一位非开发者来写它。每个标签都用**领域语言**，而不是代码：按钮和状态读起来像业务，而不是像 reducer。用平实的话解释正在发生什么。

用干净的层级从上到下排布它：

1. **标题与一行解释**，说明这个演示让你探索什么（第 1 步里的问题）。
2. **当前状态**：完整的相关状态，渲染成一个可读的面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，让变化可见。在有助于非开发者跟上的地方，点出刚才变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，这样任何人都可以任意顺序拨弄这个模型。每次点击派发它的动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个标签一个。每个标签里有一段用平实语言写的简短场景描述（它设定的情境以及要留意什么），在它下面是该场景按顺序排列的**要按的按钮**。每一步都是一个真实的按钮：点击它就执行该动作并前进到下一步。开始一个走查会重置到一个已知的初始状态，让场景每次都按同样的方式跑。

选择能演示那些别扭情形的场景，那些在纸面上难以推理的情形：顺利路径、一个刁钻的边界情况、一次对某种本应非法之事的尝试。

让它漂亮但克制：干净的排版、宽裕的间距、一种强调色。不要动画，不要花招：任何会与状态和按钮争夺注意力的东西都不要。

##### 30.1.2.4 交给他们（Hand it over）

把文件发给他们，或者替他们打开。他们会在方便的时候点完走查和自由操作；有趣的时刻是他们说「等等，这不应该可能」或「咦，我以为 X 会不一样」的时候；那些是 _想法_ 里的 bug，这正是全部要点。如果他们想要新的动作或新场景，就加上。原型会演化。

##### 30.1.2.5 捕获答案与原型（Capture the answer and the prototype）

原型回答了它的问题之后，先捕获答案，然后按 [SKILL](../../../reference/mattpocock-skills/skills/engineering/prototype/SKILL.md) 描述的方式捕获原型。逻辑专属的映射：被验证的 reducer / 状态机 / 函数集升进真实模块（决策被吸收）；HTML 外壳随行去到保留原型作为一手来源的那个一次性分支，而由于它是一个自包含文件，它在那里依然可以轻而易举地重跑。

#### 30.1.3 反模式（Anti-patterns）

- **不要加测试。** 一个需要测试的原型不再是原型。
- **不要把它接到真实数据库。** 用内存状态，除非问题专门关乎持久化。
- **不要泛化。** 不要「如果我们以后想支持 X 呢」。原型只回答一个问题。
- **不要把逻辑和页面糊在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可以被整块取出。把页面保持为覆盖在纯模块上的一层薄壳。
- **不要去够框架、打包器或服务器。** 一个接收方双击的文件；一个 React 应用或开发服务器会毁掉「可分享」。
- **不要把 HTML 外壳发布进生产。** 页面的优化目标是让人用手点完。它背后的逻辑模块才是值得留下的部分。

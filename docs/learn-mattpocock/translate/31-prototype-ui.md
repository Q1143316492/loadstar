### 31.1 UI 原型（UI Prototype）

在单一路由上生成**几个截然不同的 UI 变体**，可从一条浮动底栏切换。用户在浏览器里翻看各变体，选中一个（或从每个里偷一点），然后把其余的扔掉。

如果问题关乎逻辑/状态，而不是某物看起来怎样，这就是错的分支。用 [LOGIC.md](../../../reference/mattpocock-skills/skills/engineering/prototype/LOGIC.md)。

#### 31.1.1 何时这是正确的形态（When this is the right shape）

- 「这个页面应该长什么样？」
- 「我想在定下来之前看看这个仪表盘的几个选项。」
- 「给设置页面试一个不同的布局。」
- 任何用户本来会在脑子里花一天在三个模糊稿之间挑选的时候。

#### 31.1.2 两种子形态：强烈偏好子形态 A（Two sub-shapes: strongly prefer sub-shape A）

当一个 UI 原型**紧贴着应用的其余部分**时，判断起来容易得多：真实的页头、真实的侧栏、真实的数据、真实的密度。一个孤立的一次性路由是真空：每个变体单独看都没问题。只要有一个说得过去的现有页面可以承载这些变体，就默认选子形态 A。只有当原型确实没有附近的归属处时，才去够子形态 B。

##### 31.1.2.1 子形态 A：对现有页面的调整（首选）（Sub-shape A: adjustment to an existing page (preferred)）

路由已经存在。变体被渲染**在同一条路由上**，由 `?variant=` URL search param 控制。已有的数据获取、参数和认证全部保留。只有渲染被替换。这是默认做法；除非有具体理由不这么做，否则就选它。

如果原型的对象还没有页面，但 *本来就会自然地住在某个页面里*（仪表盘的一个新区域、设置页面上的一张新卡片、现有流程里的一个新步骤），它仍然属于子形态 A。把变体挂载在宿主页面内部。

##### 31.1.2.2 子形态 B：一个新页面（最后手段）（Sub-shape B: a new page (last resort)）

只有当被做原型的东西确实没有现有页面可以住进去时才用它（例如一个全新的顶层界面，或一条无法合理嵌入任何地方的流程）。

遵循项目已有的路由约定创建一个**一次性路由**。不要发明一个新的顶层结构。命名要让它是明显的原型（例如在路径或文件名里包含 `prototype` 这个词）。同样用 `?variant=` 模式。

在定下子形态 B 之前，做个基本检查：真的没有现有页面可以把它嵌进去吗？一条空路由会隐藏一条有内容的路由本会暴露的设计问题。

在两种子形态里，浮动底栏完全相同。

#### 31.1.3 流程（Process）

##### 31.1.3.1 陈述问题并选定 N（State the question and pick N）

默认**3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音，所以上限就定在那里。

用一行写下计划，放在原型所在处或文件顶部的注释里：

> 「设置页面的三个变体，通过 `?variant=` 切换，在现有的 `/settings` 路由上。」

无论用户是否在场提出反对，这都成立。

##### 31.1.3.2 生成截然不同的变体（Generate radically different variants）

每个变体各起草一版。每一个都要满足：

- 页面的用途以及它能访问的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，等等）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层级、不同的主要可供性，而不只是不同的颜色。三个略微调整过的卡片网格不是 UI 原型，是壁纸。如果两版草稿出来太像，就带着明确的「不要用卡片网格」指导重做其中一个。

##### 31.1.3.3 把它们接起来（Wire them together）

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：把所有已有的数据获取保留在切换器之上；每个变体只有被渲染的子树变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

##### 31.1.3.4 构建浮动切换器（Build the floating switcher）

一条小型的固定定位栏，位于屏幕底部居中，包含三部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体的 key，如果变体导出了名字，也显示那个名字。例如 B (`Sidebar layout`)。
- **右箭头**：向前循环（循环）。

行为：

- 点击箭头会更新 URL search param（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），让变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的胶囊、轻微的阴影），让它明显地不属于正在被评估的设计。
- 在生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查来把关，这样一次误合入的原型不能把这条栏发给用户。

把切换器放在一个单一的共享组件里，让两种子形态都能复用它。放在项目里共享 UI 所在的地方。

##### 31.1.3.5 交给他们（Hand it over）

把 URL（以及 `?variant=` 的各个 key）摆出来。用户会在方便的时候翻看。有趣的反馈通常是 **「我想要 B 的页头配 C 的侧栏」**，那才是他们真正想要的设计。

##### 31.1.3.6 捕获答案并清理（Capture the answer and clean up）

一旦某个变体胜出，先捕获答案（哪个变体以及为什么），然后按 [SKILL](../../../reference/mattpocock-skills/skills/engineering/prototype/SKILL.md) 描述的方式捕获原型。把胜出者折进真实代码，把其余部分移到一次性分支，而不是移进 main：

- **子形态 A**：把胜出者折进现有页面；从 main 里删掉落败的变体和切换器。
- **子形态 B**：把胜出的变体提升为一条真实路由；从 main 里删掉一次性路由和切换器。

完整的变体集合是一手来源，所以它落到一次性分支上，而不是垃圾桶里，因为留在 main 分支里的变体组件和切换器会很快腐坏，并让下一位读者困惑。

#### 31.1.4 反模式（Anti-patterns）

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上互不相同。
- **在变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁掉了要点。每个变体都应该能自由地扔掉布局。
- **把变体接到真实的变更操作上。** 只读原型没问题。如果一个变体需要变更，就让它指向一个桩：问题在于「这应该长什么样」，不是「后端能不能用」。
- **把原型直接提升进生产。** 变体代码是在原型的约束下写的（没有测试、极少的错误处理）。当你把它折进去时，要好好重写它。

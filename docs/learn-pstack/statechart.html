statechart 与验证技能家族

用 TLA+ 描述系统怎么在状态之间移动，用 TLC 穷举所有顺序，再把结果画成人能读的图。本文汇总它是什么、和哪几个技能配套、背后的理论，以及在本仓值不值得用。

整理 2026-11-23 来源 cursor/plugins 本地存档 停在 74dd229，statechart 不在其中

00一页看懂

如果只记一屏，记这四张卡。

一句话

把一个「会移动的系统」写成 TLA+ 规格，让 TLC 穷举所有状态与步序，再把违规画成最短路径的 Mermaid 状态图。

输入

一份 SPEC.tla、一份 .cfg、一个 view 模块（state() / step() / group()），外加你对「什么算错」的判断。

输出

chart.mmd（可贴进任何 Mermaid 查看器）、一份报告、tlc.out、以及按需渲染的 SVG。

成本

首次要 mise 装 TLC 和 Java，需联网；脚本是 TypeScript，要 Node 22.18–22.x 或 23.6+。只能手打 /statechart。

它验证的是模型，不是代码。模型通过只说明「这个范围内没找到反例」。所以原文要求：模型描述代码时，把每条 bug 路径回放到真代码上，复现成测试或 live repro；如果 bug 没复现，先认为模型错了。

01缩写表

先解决名字。最容易混的是同一家族里的四个词：TLA 是逻辑，TLA+ 是语言，PlusCal 是写起来更容易的方言，TLC 是跑它的检查器。statechart 不是缩写，是 Harel 1987 年那套状态图的名字，pstack 只是拿它当技能名。

TLA+ 家族

缩写全称是什么
TLATemporal Logic of Actions「动作的时序逻辑」，Lamport 的逻辑基础：状态 + 迁移 + 时序运算符。
TLA+TLA plus建在 TLA 上的规格语言，加了集合、整数、模块、函数等，能真的写规格。
PlusCal（不是缩写）TLA+ 家族里的类伪代码算法语言，编译成 TLA+。新手从这里写，比裸 TLA+ 好读。
TLCTLA+ Checker随 TLA+ 附带的模型检查器：读规格和配置，穷举状态，报反例。
TLAPSTLA+ Proof System机械化证明器。TLC 是穷举，TLAPS 是证明；后者不用跑完所有状态。
Apalache—基于 SMT 的符号模型检查器，另一种检查 TLA+ 的方式，状态爆炸时的替代。
ToolboxTLA+ ToolboxLamport 的桌面 IDE，跑 TLC 和 TLAPS。VS Code 也有社区扩展。

配置里的关键字

关键字含义什么时候写
INVARIANT每个状态都必须成立的性质（安全性）「任何时刻都不会……」「余额不会为负」
PROPERTY涉及时间的性质（活性）「请求终将返回」「告警终将被处理」
CONSTRAINT限制 TLC 探索范围的状态谓词模型状态太多，要砍掉一部分
SYMMETRY声明互相等价的状态，减少计数多个节点完全对称时
CONSTANT给规格里的常量赋值模型规模（几个节点、几个用户）

逻辑与验证

缩写全称一句话
LTLLinear Temporal Logic线性时序逻辑：在一条执行路径上谈「永远 / 终将」。TLA 的 []、<> 就是它。
CTL / CTL*Computation Tree Logic分支时序逻辑：在所有路径上量化。模型检查的另一套经典语言。
SATBoolean Satisfiability布尔可满足性：给一组布尔公式，找一组赋值让它为真。很多验证器的底层引擎。
SMTSatisfiability Modulo Theories带理论的 SAT（整数、数组、位向量）。Apalache、Alloy 都靠它。
BMCBounded Model Checking有界模型检查：只查前 k 步，编码成 SAT 求解。
wpweakest precondition最弱前置条件：从后置条件反推「最少需要什么前置条件」。

并发与分布式

缩写全称一句话
DFA / NFADeterministic / Nondeterministic Finite Automaton确定性 / 非确定性有限自动机，最基础的状态机。
wp 之外Hoare 逻辑{P} C {Q}：前置条件 P，执行 C 后必须满足 Q。
CAPConsistency, Availability, Partition tolerance分布式三选二。常被误读，但至少知道这三个词。
CRDTConflict-free Replicated Data Type无冲突复制数据类型：并发修改后能自动合并。
FLPFischer–Lynch–Paterson「异步 + 一个节点可能崩溃」下不存在确定性共识的不可能性结论。
PCTProbabilistic Concurrency Testing带概率保证的并发测试调度算法。
loom（工具名）Rust 的并发模型检查库，遍历线程交错。

02从哪开始

目标不是「学会 TLA+」，而是在一次具体的问题上用它拿到结论。路径按这个目标排。

0

半小时：跑通一次成功和一次失败

装 VS Code 的 TLA+ 扩展（微软官方，自带 TLC）。打开 learntla.com 的前两章，照抄一个三状态规格，跑一遍。

然后把某条规则改坏，让它报错。这一步的唯一产物是：你知道「TLC 报错长什么样」。

1

半天：用 PlusCal 写 pet 的会话状态机

状态就四个：idle、working、alert、destroyed。事件就五类：SessionStart、PostToolUse、UserPromptSubmit、Stop、SessionEnd。再加一个超时事件代表 tick()。

先只写 TypeOK（状态逃不出这四个值），跑通再往下。这一步的产物是一份能看懂、能改的规格。

2

半天：加两条业务不变量

例如「alert 状态下 consecutiveReads 一定 ≥ 阈值」「write 之后 consecutiveReads 一定为 0」。

跑一遍。通过就说明这两条在模型里成立；不通过就是模型或代码有一边错了，这正是你要找的东西。

3

一小时：证明检查会失败

故意删掉 noteWrite 里的清零，或者把 UserPromptSubmit 清 alert 的那行去掉，再跑。TLC 必须报错，并给出最短路径。

这个动作训练的是对工具的信任边界：没看它失败过的检查，等于没检查。

4

一小时：把反例落回真代码

把报错的路径翻译成 state.js 能跑的事件序列，写成一条测试。路径的每一步对应一个事件。

如果测试跑不出 bug，先认为模型错了，回头改模型——这是原文明确要求的顺序。

5

之后：只在有靶子的时候再用

下一次触发应该是「一个真实但复现不了的 bug」或「一个正在纠结的并发/重试设计」。没有靶子就不要建模型——形式化的成本只有在你要回答一个具体问题时才值。

替换路径：如果两天后你觉得语法还是别扭，别硬啃 TLA+。先用状态化属性测试（fast-check 的 fc.commands）做同样的事：列出不变量、随机走状态、每步检查。这个版本第二天就能进 CI，而且不需要学新语言。

必须掌握的四件事（其余的都可以查）

① 状态迁移模型state / step / next-state relation

系统 = 一组变量 + 初始状态 + 「什么步能让状态怎么变」。自测：能在纸上写出 pet 的变量、Init、以及三个最关键的 action，不查资料。

② 不变量 / 安全性 / 活性invariant · safety · liveness

「任何时刻都真」和「终将发生」是两种不同的承诺，检查难度也不同。自测：拿到一段需求，能把每句话标成安全性或活性；能说出为什么「卡住」比「崩溃」难查。

③ 原子步atomic step · linearizability

哪一步在系统里不可分割；一个检查跨越了不可分割的边界就是竞态。自测：能指出一段代码里的 check-then-act，并说出它该被包进哪个原子单位。

④ 反例 = 最短路径 + 可回放counterexample

验证的产出不是「通过 / 失败」，而是「一条能重放的步骤序列」。自测：能把一个 bug 报成不带情绪的、可复现的步骤列表，而不是「有时候会坏」。

现在不用学的

  • 定理证明（TLAPS、Coq、Isabelle）——除非你在写编译器、内核、密码学。
  • 模型检查的复杂性理论与 CTL 的不动点算法——知道「穷举 + 状态爆炸」两个词就够跟人讨论。
  • 抽象解释、精化演算、进程代数——需要时再回来，现在学只会占地方。
  • TLA+ 的模块系统、递归算子、证明语言——写第三、第四个模型时才需要。

顺序很重要：先把 ①③④ 用在 pet 上，再回头补 ② 的文献。反过来（先读论文再动手）通常会在第三页放弃——这些概念的价值要在一次真实的 bug 上才显出来。

03验证技能家族

pstack 里和「验证」有关的技能有五篇，分两条线。它们共享同一套结构：生成一个项目本地技能、记录覆盖范围、证明检查会失败、交接时说明局限。

线 A · 形式化验证 模型 / 证明 / SMT
create-formal-verification-skill 选目标、选工具，生成项目本地 verify 技能
→
statechart 读 TLA+ 检查结果：最短违规路径 + 状态图
→
maintain-formal-verification-skill 代码变了之后把模型拉回同步

工具按问题选：事件顺序会不会出错 → 模型检查（默认 TLA+）；代码本身在任意输入下对不对 → 跑在代码上的验证器；要覆盖所有规模 → 定理证明。statechart 是 TLA+ 路线指定的结果阅读器，原文要求「按名字引用它，不要抄它的命令和路径」。

线 B · 驱动真实应用 UI / CLI / 服务
create-verification-skill 面试仓库，生成 verify-<app> 技能与功能地图
→
maintain-verification-skill 按功能逐个读源码 + 实际驱动，修补漂移

这条线不碰形式化。产出物是 launch / doctor / drive / evidence / cleanup 五段，加一份 features/ 地图；维护时一个功能一个只读子智能体，主线程负责真正驱动应用。

技能干什么触发核心产出
statechart TLA+ 模型检查 + 状态图 + 最短违规路径 /statechart（禁自动调用） chart.mmd、报告、tlc.out
create-formal-verification-skill 找出最值得形式化的代码，验证一条性质，留下可复跑的本地技能 /create-formal-verification-skill 项目本地 verify 技能 + 覆盖记录
maintain-formal-verification-skill 代码变了之后更新模型并重跑，区分「验证漂移」与「真 bug」 /maintain-formal-verification-skill 四种结论：in sync / updated / bug / blocked
create-verification-skill 把「怎么启动、怎么驱动、怎么留证据」写成项目技能 /create-verification-skill verify-<app>/SKILL.md + 功能地图
maintain-verification-skill 定期审计功能地图与真实应用是否还一致 /maintain-verification-skill 最多一个 PR 的已证修正

共同设计：验证能力写成项目本地技能，而不是一次性脚本；覆盖范围与「上次核对到的 commit」写进技能；每次都要求先看到它失败一次；衔接时说明边界与假设。这四条和具体工具无关，是这套技能真正可搬的部分。

04运行流程与产物

五步。判断在工作量最大的两处：规则怎么写成不变量、图上的词怎么说成人话。

1

写规格：变量、Init、Next

每条「读者认可的规则」写成 INVARIANT。规则没有对应变量就加变量；不要为了让它成立而放宽规则。Next 写成各 action 的析取，否则 TLC 把每一步都叫 Next。终态补一个 no-op action，否则 NoDeadlock 会误报。

2

写 view：决定图长什么样

state(vars) 返回字符串 → 平铺图；返回数组 → 父子层级；返回对象 → 每个键一个并行区域。step(action, from, to) 决定箭头文案，group() 与 colors 决定配色，title 是标题。

标签用读者看得见的事（「正在付款」「租约已持有，写入待定」），不出现变量名；箭头写「你按下播放」「连接失败」，不写 action 名。同一个标签里的步不会画出来——需要读者看见，就拆标签。

3

跑命令

<skill dir>/scripts/statechart SPEC.tla \
  [--config FILE] [--view FILE] [--out DIR]

首次运行用 mise 安装 TLC 和 Java，需要联网。原生 Windows 上用 node --disable-warning=ExperimentalWarning scripts/statechart.ts。

4

读报告

每条违反的规则给出最短路径，按报告编号讲给人听。规则坏掉后 TLC 会继续往前走，所以图上能看到「出 bug 之后」的状态。规则没检查到的会列在「Rules not checked」下——那里面的规则成立与否未知。

5

交接

把图与 Mermaid 文本交给要做决定的人；每条 bug 一行：规则、人话描述的规则、路径编号。说明模型省略了什么，以及重新生成文件的命令。模型描述真实代码时，把每条路径回放成测试或 live repro。

产物与预算

产物 / 上限内容
chart.mmdMermaid 状态图。直接贴成 mermaid 代码块给用户看；要图片时按 render.md 用 Pele 渲染成 SVG。
报告每条规则的检查结果、最短路径、未检查的规则、状态计数、被隐藏的步。
tlc.out / tlc-<RULE>.out按原配置跑出的 TLC 输出；后者是找到某条违规那次运行的输出。
约 20 个箭头图的可读预算。超了就先合并语义相同的状态，再整条箭头地隐藏不必要的步。
500 个图状态超过后只画通往违规状态的路径；没有违规就不写 chart.mmd。
100,000 个状态第一次发现违规之后的每次运行在此上限停止，防止大模型跑不完。
1 个 worker原文说明：按配置原样检查，单 worker。

一个最小规格

---- MODULE Checkout ----
EXTENDS Naturals

VARIABLES phase

Init  == phase = "idle"
Start == phase = "idle"   /\ phase' = "paying"
Pay   == phase = "paying" /\ phase' = "paid"
Fail  == phase = "paying" /\ phase' = "failed"
Done  == phase \in {"paid", "failed"} /\ UNCHANGED phase  \* 终态自环

Next  == Start \/ Pay \/ Fail \/ Done
vars  == <<phase>>
Spec  == Init /\ [][Next]_vars

TypeOK  == phase \in {"idle", "paying", "paid", "failed"}
====

示意用，不是上游原文；状态名与动作名按你的建模替换。

05TLA+ 与 TLC

两个词，一个语言，一个检查器。分清楚它们各自的边界，比记住语法重要。

TLA+ · 语言

Lamport 的形式化规格语言。写三样东西：变量（状态）、Init（初始状态）、Next（怎么迁移，x' 表示下一步的 x）。再加规则：INVARIANT（每一刻都真）或 PROPERTY（涉及时间）。

它不执行、没有 I/O。建模的是设计，不是代码。

TLC · 检查器

从 Init 出发广度优先穷举所有可达状态与步序，在每个状态上检查不变量。状态去重，所以找到的反例是最短路径。

天花板是状态爆炸：靠小常量、CONSTRAINT 上界、状态上限控制。

三个运算符，够读大多数规格

写法意思属于
[]P在每条执行的每一刻，P 都成立安全性（永不）
<>P在每条执行的某个时刻，P 成立活性（终将）
P ~> Q只要 P 发生，之后 Q 终将发生活性，「响应」形状

有界穷举 ≠ 证明。通过只表示「这个范围内没找到反例」。要「所有规模都成立」得进定理证明（TLAPS、Coq/Isabelle）；要验证代码本身（内存安全、溢出）得换跑在代码上的验证器。这句话决定了这个技能该用在什么地方、报告该怎么写。

安全性与活性的差别，为什么值得单独记

  • 安全性（坏事永不发生）：反例是有限的一段步骤，容易被找到和复现。
  • 活性（好事终将发生）：任何有限前缀都不能判定对错，必须看整条无限执行。所以「卡住不动」「永远转圈」这类 bug 天生比崩溃难查——这是理论层面的难，不是工程不努力。

06图上的标记

四种标记是判断「哪里出事」的入口，颜色与状态图一致。原文把颜色当建议：可以换，但要保持语义。

breaks · 违反规则 mayBreak · 部分模型状态违反 bugPath · 最短路径上的状态 repeats · 反例中永远重复
标记 / 概念何时出现读的时候注意
breaks这个标签背后的所有模型状态都违反某条规则两条规则同时坏时，图例会把它们写在同一处；交接时必须说清哪个状态坏了哪条规则。
mayBreak只有部分模型状态违反合并状态会把它变成 mayBreak，等于藏起「到底在哪一步坏」；不要合并违反不同规则的两个状态。
bugPath最短违规路径经过的状态路径按报告编号讲；回放时一步对应一个 action。
repeatsPROPERTY 反例永远重复的那部分说明这是稳定的循环，不是偶发。
并行区域state() 返回对象一个组合能违规而没有任何状态被标记时，组合里每个状态都会被标记——标记是组合级的，不是单状态级的。

顺序与隐藏

如果图太忙，先让 state() 返回更粗的标签，再对不必要的步返回 null 来隐藏箭头。隐藏有硬约束：每个图状态仍要能从起点到达；每个有出口的状态至少保留一条出边；一条箭头的步要么全藏要么全不藏；交接时说明藏了哪些。

07七条反模式

这个词不是原文的章节名，是从原文一堆规则里归纳出来的一类错误：把检查做得一定能通过，或把图做得一定没人读懂。

反模式后果原文对应的规则
照着代码逐行建模 状态爆炸，且把实现细节当成设计问题 建模针对设计；常量取小或加 CONSTRAINT
为了让检查通过而放宽规则 检查失去意义；真实 bug 被吃掉了 「Never weaken a rule to make it hold」；bug 只报告，不改业务代码迁就模型
原子性搞错 把实际会被打断的步骤当成一步走完，正好藏起要查的竞态 代码里一个不可分割的步，模型里也是一个步
不设边界 状态空间无限，TLC 跑不完 常量取小，或加 CONSTRAINT；第一次违规后每次运行停在 10 万状态
检查从没失败过 没验证过检查能失败，等于没检查 在故意改坏的版本上跑一遍，必须报错；maintain-formal-verification-skill 第 5 步同样要求
把模型通过当成系统正确 模型与代码脱节，通过的是过时的描述 把 bug 路径回放到真代码；「如果 bug 没复现，先认为模型错了」
模型太细 / 标签太碎 图超过约 20 个箭头就没人读得懂 先粗后细合并状态；藏步时保住可达性与出口；说明藏了什么

几条看起来像怪癖、其实是防御的规则

  • 终态必须加 no-op 自环——否则 NoDeadlock 把「正确的结束」当成死锁。
  • Next 写成 action 的析取——否则 TLC 把每一步都命名为 Next，路径无法读。
  • 并行区域里不要用方括号给「另一个区域的条件」加注——命令会自动加上，两者叠加会让两条箭头看起来一样。
  • 一步不出标签就不画——要读者看见这种步，就得拆标签。
  • state() / step() / group() 只能依赖参数——它们每个模型状态最多被调用一次，图与报告必须一致。

08理论谱系与出处

这些名词各自挂在一棵明确的谱系上。按「你关心哪一层」读，不需要从头啃。

① 状态与迁移「状态机」本身

有限自动机 → Statecharts 加了层级、并行区域、正交状态 → 时间自动机给状态迁移加时钟约束。state() 三种返回形状（字符串 / 数组 / 对象）分别对应平铺、层级、并行。

Harel 1987（statechart 名字的出处）· Alur & Dill, TCS 1994 · UPPAAL · W3C SCXML 2015

② 安全性 / 活性「永不」和「终将」

时序逻辑 LTL / CTL 把你说的「永远」「终将」形式化。安全性与活性的严格定义解释了为什么「偶发卡住」比「偶发崩溃」难查。

Lamport 1977（提出这对术语）· Alpern & Schneider 1987（形式定义）· Pnueli 1977（时序逻辑进程序验证）· Manna & Pnueli 1992

③ 验证手段穷举、有界、抽象、证明

TLC 属于模型检查：用穷举代替证明，代价是状态爆炸。BMC 把它编码成 SAT；抽象解释把无穷状态压成有限抽象；Alloy 是「轻量形式化」，只查结构与不变量、不碰时间。

Clarke & Emerson 1981 / Queille & Sifakis 1982（2007 图灵奖）· Baier & Katoen 2008（最好的一本教科书）· Jackson, Software Abstractions · Cousot & Cousot 1977

④ 原子性与并发「哪一步不可分割」

Hoare 逻辑给出前置 / 后置 / 不变量；wp 演算解释守卫命令与原子步；Owicki–Gries 与 rely–guarantee 解决多线程下的不变量；线性一致性给「一次操作看起来原子发生」一个精确判据——它就是判断「一次状态迁移是不是原子的」的标尺。

Hoare 1969 · Dijkstra 1975/1976 · Owicki & Gries 1976 · Jones 1983 · Reynolds 2002 · Herlihy & Wing 1990

⑤ 工程化不装工具也能用的版本

契约式设计把不变量写进接口；DDD 聚合把「一个事务只改一个聚合」变成原子步约束；状态化属性测试在随机游走状态空间并检查不变量——本质是小规模的 TLC；确定性仿真让同一个种子必复现。

Meyer 1992 · Evans 2003 · QuickCheck 2000 · proptest-state-machine / fast-check · FoundationDB 的 deterministic simulation

最小阅读清单

  1. Alpern & Schneider, Recognizing Safety and Liveness — 建坐标系，短。
  2. Harel, Statecharts — 解释你凭直觉画的图为什么长那样。
  3. Lamport, Specifying Systems（作者主页免费）— 前三章加一两个案例就够判断要不要用。
  4. Jackson, Software Abstractions — Alloy，比 TLA+ 便宜得多。
  5. Herlihy & Wing, Linearizability — 原子性的判据。
  6. Erlang QuickCheck 的状态化测试手册 / proptest-state-machine 文档 — 第二天就能用。

性价比最低的是定理证明；最高的是 Alloy 与状态化属性测试。

09落到本仓

本仓有一个规模刚好的状态机：agent/client/pet/state.js。5 个状态、4 类事件、一个定时器，且已经有 smoke 测试。

成本做法适合
零把不变量写成一句话；区分「永不 / 终将」；先声明原子步；bug 报告写成步骤序列设计、评审、排查的日常
低断言式检查：在日志 / debug 面板里随时校验不变量pet 这类长期运行的服务
低属性测试（fast-check）：随机生成事件序列，每步检查不变量state.js，现成 Node 测试就能接
中手写状态表 + 穷举小状态空间的测试状态机
高TLA+ / TLC并发、协议、状态机真的出事且测试覆盖不到

pet 可以借的四条不变量

  • consecutiveReads 只在 read 时增长、write 时清零；不会凭空变化。
  • 一个 session 不会从 destroyed 复活。
  • alert 只由 read 触发；UserPromptSubmit 或 write 才清除。
  • 任何时刻，alerts 计数等于处于 alert 的 session 数（聚合与明细一致）。

已有的一处活性缺口：tick() 只把 working 降级为 idle，不会清除 alert。会话如果突然没有事件，alert 会不会一直亮着？这属于「活性没定义」——是不是有意为之，值得先问一句再决定改不改。

建议的路径

先做属性测试，不碰 TLA+。列出 3–4 条不变量，用随机事件序列去冲它们；这比装 TLC 便宜一个数量级，而且能进 CI。TLA+ 留到「pet 真的出现过难复现的卡死」再考虑——那时你手里有具体反例，验证才有靶子。

判断依据：形式化验证覆盖的是「顺序」维度，测试覆盖的是「输入」维度。pet 的风险集中在会话事件的顺序与定时器边界上，所以状态化属性测试命中率最高；TLA+ 的价值要等复杂度（多实例、多进程、真实并发）上来之后才显现。

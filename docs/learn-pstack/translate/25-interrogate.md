# Interrogate

对配置里的每个模型各拉起一名评审者，对抗式地评审代码改动。每个模型拿到**同一份**提示与评分表。对抗信号来自**模型之间的差异**，不是给它们分配角色人设。模型在盲区、先验与推理方式上各不相同。跨模型一致的发现是高置信信号；只有单一模型提出的发现值得读，但置信度较低。

交付物是一份**综合后的裁决**。**不要**自动应用改动。

## 第 1 步 确定范围

从上下文里认出要评审什么：

- 用户点了具体文件或一段 diff，就用它
- 在特性分支上，跑 `git diff main...HEAD`（或对应的基线分支）取出完整改动集
- 用户的消息提到最近的工作，就收集相关文件

把 diff（或文件内容）打包，连同评审者理解代码所需的周边上下文文件一并给出。

## 第 2 步 陈述意图

拉起评审者之前，先把**意图**明确写出来：这段代码想达成什么？从这些地方推导：

- 用户的消息
- 提交信息
- 如果有 PR 描述，也包括它
- 代码本身

写成一整段清楚的文字。评审者挑战的是「这份工作是否很好地达成了意图」，不是「意图本身对不对」。意图拿不准时，先问用户再往下走。

## 第 3 步 拉起评审者

对配置的 interrogate 清单里的每个模型各拉起一名评审者（默认 `claude-opus-4-8-thinking-xhigh`、`gpt-5.5-high-fast`、`composer-2.5-fast`），全部放在**同一条消息**里。

每名评审者：

- `subagent_type`：`generalPurpose`
- `model`：配置的 interrogate 清单里的一个模型
- `readonly`：`true`

如果某个配置的模型 slug 在拉起子智能体时被判为无法解析，查看 Task 工具报错信息里给出的合法 slug，挑最接近的等价模型（优先同家族的最高推理档），用合法 slug 拉起，另开一个 PR 去更新配置里的默认值。**不要**让 slug 问题卡住评审。

读 `references/reviewer-prompt.md`，把模板填好：

1. 第 2 步陈述的意图
2. diff 或文件内容
3. `references/rubric.md` 里的评审评分表
4. `references/code-quality-review.md` 里的代码质量镜头

**同一份**填好的模板发给所有评审者，这样每个模型都会用上代码质量镜头。

每名评审者按提示模板里描述的那样产出结构化发现。

## 第 4 步 综合

结果陆续回来时，拼出一幅统一的图景：

1. **解析全部发现**，来自所有评审者
2. **找出共识。** 被 2 个以上模型**独立**提出的发现，信号最强。
3. **找出单模型发现。** 仍然值得读，但按此加权。
4. **去重。** 不同模型可能用不同说法描述同一个问题。合并它们，并注明有哪些模型提出。
5. **记下分歧。** 一个模型标出某问题、另一个模型明确说相反结论时，那是对裁决有用的上下文。

## 第 5 步 主审裁决

你是主审，一名务实的资深工程师，不是中立的汇总器。

完整框架见 `references/lead-judgment.md`。评审者只看到代码库的一个切片；你拥有完整上下文（目标、约束、时间线、哪些取舍已经考虑过）。**放手用这份上下文。**

把每条发现归入下列一档：

- **Act on（动手）。** 在实际目标下真正影响正确性、安全性或可维护性的问题。这类问题会挡住一个真实的 PR。
- **Consider（考虑）。** 站得住的意见，但你不确定它现在是否值得付出处理的成本。值得用户注意。
- **Noted（记下）。** 技术上成立，但不可行动：取决于上下文、过早优化，或按当前阶段影响很小。
- **Dismissed（驳回）。** 错的、吹毛求疵的，或缺上下文。用一句话说明为什么。

每条发现都要带上：

- 哪些模型提出了它
- 所属档位（act on / consider / noted / dismissed）
- 一句话的归类理由

## 输出格式

按这个结构呈现裁决：

### Intent

> [第 2 步写下的意图段落]

### Reviewers

每名评审者一行，形如 `- <模型名>: [N 条发现]`

### Act On

[应当处理的发现。每条包含：描述、哪些模型提出、为什么重要。]

### Consider

[值得考虑的发现。每条包含：描述、哪些模型提出、牵涉的取舍。]

### Noted

[成立但优先级低。简短列表。]

### Dismissed

[被驳回的发现与简短理由。这向用户展示过滤掉了什么、为什么，这样用户不认同你的判断时可以推翻它。]

### Agreement Map

[模型在哪里一致、在哪里分歧，以及这种一致 / 分歧的模式告诉了我们什么？]

# 评审者提示模板

用这份模板的占位符构造每个评审子智能体的提示。

---

你是一名对抗式代码评审者。在下面的代码里找真实问题：bug、设计缺陷、安全问题、可维护性隐患。你的职责不是提供帮助或鼓励，而是**压力测试**。

## 意图（Intent）

作者为这次改动陈述的意图：

> {INTENT}

你要评审的是：代码是否很好地达成了这个意图。**不要**质疑意图本身。假定目标是正确的，挑战的是执行。

## 被评审的代码

{DIFF_OR_FILES}

## 评审评分表

{RUBRIC_CONTENTS}

## 代码质量镜头

{CODE_QUALITY_CONTENTS}

## 指示

用上面评分表与代码质量镜头里所有**适用**的镜头评审代码。不适用的镜头不要硬套。一个简单的 bug 修复不需要大段讨论架构完整性。

每条发现都要给出：

1. **严重度（Severity）**：`critical` | `warning` | `nit`
   - `critical`：会导致 bug、数据丢失、安全问题，或根本性错误行为
   - `warning`：设计顾虑、可维护性风险，或尚未立刻坏掉但将来必会带来痛苦的正确性问题
   - `nit`：风格、命名、小幅改进。只在确实有用时才写 nit，不要为了凑篇幅。
2. **发现（Finding）**：问题是什么，用具体措辞说清。引到具体的行 / 函数。
3. **证据（Evidence）**：你为什么认为这是问题。**展示推理过程**，不要只下断言。
4. **建议（Suggestion，可选）**：你打算怎么改，如果你有具体替代方案。没有明确改法就跳过这一项。

## 什么算一条好发现

- 它引用具体代码，而不是含糊的顾虑（「这里可以更好」）
- 它解释**为什么**是问题，而不只是说**是**问题
- 它区分「这坏了」与「我会换一种写法」
- 它考虑陈述过的意图。忽略「正在构建什么」这一背景的发现，是坏发现

## 要避免的

- 复述代码做了什么，却没指出任何问题
- 因为自己更偏好别的风格，就要求重写能工作的代码
- 提出没有证据表明可达的假设性问题（「万一有人传 null 进来呢」）
- 赞美代码。你是对手，不是啦啦队。什么都没发现问题，就说「无发现」，然后停。

## 输出

把发现作为一个结构化列表返回。零发现就直说。**空评审是合法结果。**

```
## Findings

### 1. [Severity] Short title
**Location**: file:line or function name
**Finding**: What's wrong
**Evidence**: Why this matters
**Suggestion**: (optional) What to do instead

### 2. [Severity] Short title
...
```

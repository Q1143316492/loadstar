## 8 task-reviewer-prompt

> 译自 `reference/superpowers/skills/subagent-driven-development/task-reviewer-prompt.md`（原文 207 行）。提示词块（原文第 10–188 行）保留原结构，内容已译；原文见 `skills/subagent-driven-development/task-reviewer-prompt.md:10-188`。块外的说明文字全译；命令、文件路径、占位符与标识符（`[BASE_SHA]`、`[DIFF_FILE]`、`Approved`、`Critical`、`Important`、`Minor`、`✅/❌/⚠️` 等）按原样保留。
> 对照 `READING-superpowers.md` 第 09 项。

派发任务评审者子智能体时使用这份模板。评审者只读一次该任务的 diff，返回两项裁决：spec 合规与代码质量。

**目的（Purpose）：** 核实一个任务的实现与它的需求相符（不多、不少），并且造得好（干净、有测试、可维护）

```
Subagent (general-purpose):
  description: "评审 Task N（spec + 质量）"
  model: [MODEL — 必需：按 SKILL.md 的 Model Selection 选择；省略的
         模型会静默继承本会话最贵的那个]
  prompt: |
    你在评审一个任务的实现：先看它是否与需求相符，再看它是否造得好。这是一道任务范围的闸门，不是合并评审——一次宽泛的整分支评审会在所有任务完成之后单独进行。

    ## 要求了什么（What Was Requested）

    读任务简报：[BRIEF_FILE]

    来自 spec/设计、约束本任务的全局约束：
    [GLOBAL_CONSTRAINTS]

    ## 实现者自称造了什么（What the Implementer Claims They Built）

    读实现者的报告：[REPORT_FILE]

    ## 待评审的 Diff（Diff Under Review）

    **基准（Base）：** [BASE_SHA]
    **头提交（Head）：** [HEAD_SHA]
    **Diff 文件（Diff file）：** [DIFF_FILE]

    只读一次 diff 文件——它包含提交列表、一份统计摘要、以及带上下文的完整 diff，它就是你观察这次改动的视图。diff 的上下文行**就是**被改动的文件：不要单独 Read 一个被改动的文件，除非你必须判定的某段 hunk 在函数中间被截断了——真遇到就要在报告里说明。不要重跑 git 命令。如果 diff 文件缺失，自己取 diff：`git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。不要爬更广的代码库。只为了评估一个你能点名的具体风险，才去看 diff 之外的代码——每个点名的风险做一次聚焦的检查，并在报告里把风险和你检查了什么一起点名。横切改动是合理的点名风险：如果 diff 改动了锁的顺序、某个函数或 API 契约、或共享可变状态，检查调用点就是正确的方法。

    你对这个检出的评审是只读的。不要以任何方式改动工作树、索引、HEAD 或分支状态。

    ## 你不派发子智能体（You Do Not Dispatch Subagents）

    这一切评审都由你自己做完。绝不要生一个子智能体去评审 diff 的某一部分，也绝不要为了要第二个意见再生一个评审者。本流程已经为这项工作提供了它该有的每一个评审席位；你生的评审者会在满额成本下重复其中一个席位，而它的裁决一文不值。如果 diff 大到一次读不完，就自己分几次读完，并在报告里说明。

    ## 不要相信报告（Do Not Trust the Report）

    把实现者的报告当作关于代码的、**未经核实的说法**。它可能不完整、不准确、或过于乐观。拿这些说法去对照 diff 核实。报告里的设计理由同样是说法：「按 YAGNI 留着了」「故意保持简单」，或任何别的辩解，都是实现者在给自己打分。**就代码本身评判代码**——陈述出来的理由绝不降低一条发现的严重程度。

    ## 测试（Tests）

    实现者已经跑过测试，并对正是这段代码报告了带 TDD 证据的结果。不要重跑测试套件来确认他们的报告。只有当读代码冒出一个具体的疑问、而现有的任何一次运行都回答不了它时，才去跑一个测试——而且是一个聚焦的测试，绝不是一个包级别的整套测试、一次竞态检测器运行、或重复/高次数的循环。如果看起来需要重验证，在报告里建议它，而不是去跑它。如果你在这个环境里跑不了命令，就点名你会跑的那个测试。

    实现者报告的测试输出里的警告或其他噪音**就是发现**——测试输出应当是干净的。

    你看不见的证据，不等于不存在的证据。如果报告或它的测试证据看起来被截断了，或者你找不到它声称的那些结果，就按它写明的路径重新读那个文件——如果它确实缺失或乱码，把它作为一条缺口报告给控制器。重跑测试套件来重新生成你没读到的东西，不是核实；证据难以辨认，不等于证据无效。

    ## 第 1 部分：Spec 合规（Part 1: Spec Compliance）

    拿 diff 对照「要求了什么」：

    - **缺失（Missing）：** 他们跳过、漏掉、或声称做了却没实现的需求
    - **多出（Extra）：** 没有被要求的功能、过度设计、不需要的「锦上添花」
    - **理解错误（Misunderstood）：** 对的功能造错了方式、解错了问题

    如果简报列了多个文件、每个文件各有自己的改动（一次打包派发），就逐个文件拿 diff 对照那份清单：清单上每一个文件都必须有对应的 hunk。清单上列了、而 diff 始终没有触碰的文件，就是一条「缺失」发现，无论这批里其余部分看起来多干净。

    如果某条需求仅凭这份 diff 无法核实（它活在未改动的代码里，或横跨多个任务），就把它作为一条 ⚠️ 条目报告，而不是扩大你的搜索范围。

    ## 第 2 部分：代码质量（Part 2: Code Quality）

    **代码质量（Code quality）：**
    - 关注点分离干净吗？
    - 错误处理得当吗？
    - 是没过早抽象的 DRY 吗？
    - 边界情况处理了吗？

    **测试（Tests）：**
    - 新增和改动的测试验证的是真实行为，而不是 mock 吗？
    - 这个任务的边界情况被覆盖了吗？

    **结构（Structure）：**
    - 每个文件是否有一个明确的职责、以及一个定义清晰的接口？
    - 各个单元是否被拆解到可以被独立理解和测试？
    - 实现是否遵循了计划里的文件结构？
    - 这次改动是否造出了已经很大的新文件，或者显著增大了既有文件？（不要标记本来就存在的文件大小——聚焦这次改动贡献了什么。）

    你的报告应当指向证据：每条发现、以及任何你本来只会用一个光秃秃的「是」来回答的检查，都要给出 file:line 引用。一份引用行号的紧凑报告，能给控制器它需要的一切。

    你的最终消息就是报告本身：直接从 spec 合规的裁决开始。每一行要么是一条裁决、要么是一条带 file:line 的发现、要么是你跑过的一次检查——不要开场白，不要叙述过程，不要收尾总结。

    ## 校准（Calibration）

    按**实际严重程度**给问题分类。不是所有东西都是 Critical。Important 意味着这个任务在修好之前不可信：行为不正确或脆弱、漏掉的需求、或你会因此拦住一次合并的可维护性损伤——逻辑块的逐字复制、被吞掉的错误、什么都不 assert 的测试。「覆盖可以更广」以及打磨类建议是 Minor。
    如果计划或简报明确要求的东西，被这套标准判为缺陷（什么都不 assert 的测试、逻辑块的逐字复制），**那它就是一条发现**——作为 Important 报告，并标注 plan-mandated。计划的作者身份不能给自己的作品打分；由人来决定。
    在列举问题之前，先承认做得好的地方——准确的称赞能帮实现者相信其余反馈。

    ## 输出格式（Output Format）

    ### Spec 合规（Spec Compliance）

    - ✅ 符合 spec | ❌ 发现问题：[缺少/多出/理解错误的部分，附 file:line 引用]
    - ⚠️ 无法从 diff 核实：[仅凭 diff 无法核实的需求，以及控制器应当去查什么——与你核实过的所有内容的 ✅/❌ 裁决并列报告]

    ### 优点（Strengths）
    [哪里做得好？要具体。]

    ### 问题（Issues）

    #### 严重（Critical，必须修）
    #### 重要（Important，应当修）
    #### 次要（Minor，锦上添花）

    对每条问题：file:line、哪里错了、为什么重要、怎么修（如果不明显）。

    ### 评估（Assessment）

    **任务质量（Task quality）：** [Approved | Needs fixes]

    **理由（Reasoning）：** [1–2 句技术评估]
```

**占位符（Placeholders）：**
- `[MODEL]` — 必需：评审者模型，按 SKILL.md 的 Model Selection 选择
- `[BRIEF_FILE]` — 必需：任务简报文件（`bash scripts/task-brief PLAN N`
  打印它的路径；与实现者所用的同一份文件）
- `[GLOBAL_CONSTRAINTS]` — 从计划的 Global Constraints 一节或 spec 里
  逐字抄下的有约束力的要求：确切的取值、格式、以及被明确声明的组件间关系（不是流程规则——那些已经在这份模板里了）
- `[REPORT_FILE]` — 必需：实现者把它的详细报告写进去的那个文件
- `[BASE_SHA]` — 本任务之前的提交
- `[HEAD_SHA]` — 当前提交
- `[DIFF_FILE]` — 必需：控制器把评审包写到的路径（`bash scripts/review-package PLAN_FILE BASE HEAD` 打印它写出的唯一路径；评审包永远不进控制器的上下文）

**评审者返回（Reviewer returns）：** Spec 合规裁决（✅/❌/⚠️）、优点、问题（Critical/Important/Minor）、任务质量裁决

# 工作流设计笔记

> 2026-10-13 · **初步想法，未定稿**。整篇都可以被推翻。
> 这是一份一次性的上下文恢复笔记，不是权威文档；预计在一两次变更后失去价值。真正的产物在 `workflow/`。

## 1. 要去哪

一套自己的 AI 工作流，覆盖四件事：**理解新代码库 · 重构 · code review · 测试**。

**核心原则：不教 AI 干活。**

不用 superpowers 那套措辞纪律（禁令 + 反驳表 + 红旗清单 + 措辞微测）。它把不变量寄托在说服力上，换模型或换版本就可能失效，而且维护精力全花在调措辞上——要的是让流程**绕不过去**，不是让措辞**更有说服力**。

## 2. 为什么要做（问题诊断）

上一轮尝试的三个症状，和各自的机制：

| 症状 | 机制 |
|---|---|
| 文档**笼统** | AI 读不完大库 → 自动总结 → 输出"平均化的描述"。「详细一点」救不了它 |
| **容易遗漏** | 文档里全是**不可验证的部分列举**，读者无从知道有没有漏 |
| **流程过重** | OpenSpec 三件套太重，轻量任务用不上 |

**笼统的可执行判据**（替代「详细一点」）：

> 拿这个库里一个真实 issue，只用这份文档，能不能定位到该改哪个文件？
> 能 → 够具体；不能 → 它笼统，无论写得多长。

**遗漏的解药是让覆盖可见，不是写得更全。**
「入口只有 3 个：a / b / c（验证方式：…）」远比「核心模块包括 A、B、C」有用——读者立刻知道自己看全了没有。

**学习文档的正确形状**：地图 / 索引 / 路径三者中，AI 只产出第一种且低分辨率，真正缺的是后两种。**路径（一次端到端的具体追踪，每行带 `file:line`）是学习的基本单位。** 笼统的技术定义就是：句子里没有可跳转的锚点。

## 3. 当前思考

### 3.1 四层模型（最核心的一条）

技能内容按「填哪种缺口」分四层，越往下越稳定、越不费措辞：

```
4  环境层   钩子 / CI / lint / 测试命令      一次性投入，跨模型 100% 稳定
3  纪律层   "压力下别偷懒"                   极高措辞成本，跨模型最不稳定   ← superpowers 在这
2  流程层   谁先谁后 / 产物长什么样           中等成本，跨模型稳定           ← matt 大部分在这
1  信息层   本仓的事实：地图 / 词汇 / 缝隙      最低成本，跨模型 100% 稳定
```

- **规则**：写任何祈使句之前，问三次能不能下沉；三问都沉不下去的才留在第 3 层。
  （「必须每次跑测试」→ CI job；「用我们的命名习惯」→ 规范文件）
- **关键**：第 2 层约束**产物**，不约束**手法**。约束放进步骤顺序里，不放进形容词里。
  例：matt 的 tdd 写「未确认的接缝上不写任何测试」（门槛是一个产物：缝隙清单），
  而不是「你必须先写测试」。
- 第 3 层不能为零，但它应该是**残余**，不是地基。碰上了优先引进别人压测过的。

### 3.2 依赖顺序（和最初列的顺序相反）

原以为四件事并列。实际上第四件是前三件的地基：

```
理解代码库  ──>  产出：架构地图 · 领域词汇 · 缝隙清单 · 规范 · 命令
                        │
        ┌───────────────┼───────────────┐
        v               v               v
      重构            测试           review
```

三个改造类技能本身几乎不用自定义，它们需要的只是**读这些产物**——比如 review 的 Standards 轴，在写出本仓规范之前是空的。

### 3.3 存储分工

| 存什么 | 存哪 | 谁写 |
|---|---|---|
| 系统做什么（what） | OpenSpec `specs/` | archive 流量 |
| 代码在哪（how/where） | 目标仓库里的一个目录 | 学习技能 |
| 领域词汇 | `GLOSSARY.md` | grilling / domain-modeling |

**一条纪律**（抄 `improve-codebase-architecture`）：巡检报告写临时目录、**不进仓**；导览进仓、跟着代码演进。

### 3.4 计划层的三档路由器

| 档 | 存哪 | 判据 |
|---|---|---|
| 0 | 不入文件 | 想清楚就是产物 |
| 1 | IDE plan mode | 一个会话能做完；会话结束即蒸发 |
| 2 | OpenSpec change | **状态必须活过会话**：跨会话 / 要评审 / 改持久规格 |

**升级信号**（四条任意一条成立就升级）：① 会话快满（smart zone ≈ 150k）② 需要第二个人看 ③ 会改持久规格 ④ **今天做不完**（最实用的一条）。

三者是正交的，不存在「混用」问题：plan mode 是**交互界面**（在哪想），OpenSpec 是**存储 + 状态机**（存哪），技能是**程序**（怎么想）。

### 3.5 真正要写的比想象中少

只有三样从零写：**① 理解代码库技能 ② 路由器 ③ 信息层文件**。
其余（重构 / review / 测试）全部是**提取上游 + 改指针**，因为上游技能本来就在读这些产物。

## 5. 已否决的（省得重复讨论）

- **不用 ADR** —— `ADR-FORMAT.md` 要求「难逆转」才写，而这里的决策明确预期会被推翻；且读 `docs/adr/` 的那 5 个技能是**别人的仓库在代码库上跑的**，本仓库没有代码，写了不会被读。互操作性的理由不成立。
- **不用 superpowers 的措辞纪律** —— 见 1 与 3.1。
- **不把这次的讨论记成 OpenSpec change** —— 设计还在迷雾里，围着移动靶画靶纸。等第 1 轮试跑后再说。
- **不记对话原文** —— 过程会变成 `sediment`（只增不减的沉积层）。思考压缩后的形式就是结论 + 开放问题；对话本身在会话日志里，`retro` 能检索到。

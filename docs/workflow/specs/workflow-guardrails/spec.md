## 问题陈述

我的技能库有 20 个技能、几十份文档，但仓库**没有任何自动化检查**：没有 CI、没有 hook、没有脚本。每次改动后的机械校验——文件编码是否无 BOM、frontmatter `name` 是否等于目录名、兄弟链接是否可解析、跨技能引用是否指向存在的技能、文档里复写的技能计数是否一致、地图票面字段是否合法——都靠人工回忆或让 agent 临时敲命令。漏检的代价是真实的：改名后残留旧引用、地图票指向不存在的票，这类问题只有下次读到时才会发现。

同时，agent 的运行环境在**反复打断我**：一次研究任务产生 20 次网络抓取，一次调查产生 14 条终端命令，几乎每条都要我确认；而那次跑了 52 分钟的研究子智能体，产出**一个字节都没落盘**——它把写盘放在最后，被截断后成果只存在于调试日志里。

## 解决方案

三件事，一个闭环：

1. **一条命令做完全部机械检查**，红绿分明、点名叫文件。它从磁盘算出事实（技能数、引用、链接），而不是复述文档里的结论。
2. **研究任务不再丢产出**：先写盘再深挖、抓取有预算、主控回读验证。
3. **环境不再逐条打断**：常用只读命令与信任域自动批准；危险命令仍然要问；agent 在干什么随时可见。

## 用户故事

1. 作为库的维护者，我想用一条命令跑完所有机械检查，以便不必回忆"上次都查了哪几项"。
2. 作为库的维护者，我想让检查告诉我"哪个文件、哪一行"违规，以便直接去修。
3. 作为库的维护者，我想在改技能名之后立刻知道哪里还引用旧名，以便不留下幽灵引用。
4. 作为库的维护者，我想在新增技能后发现三处文档的计数不一致，以便文档不会悄悄漂移。
5. 作为库的维护者，我想在文件被写成 GBK 或带 BOM 时当场报红，以便中文文档不会在无感知中损坏。
6. 作为库的维护者，我想在 frontmatter `name` 与目录名不一致时报红，以便技能能被正确发现。
7. 作为库的维护者，我想在兄弟文档链接指向不存在的文件时报红，以便文档可导航。
8. 作为库的维护者，我想在跨技能调用指向不存在的技能时报红，以便"调用不存在的技能"这种静默失败不会存活。
9. 作为库的维护者，我想在地图票面的 `类型/状态/阻塞于` 取值非法时报红，以便地图状态机不被写坏。
10. 作为库的维护者，我想在地图「已定决策」指向不存在的票时报红，以便索引不腐烂。
11. 作为库的维护者，我想确认检查**确实会报红**（而不只是"跑过没报错"），以便区分"检查通过"和"检查什么都没做"。
12. 作为库的维护者，我想让检查保持只读，以便它可以在任何时刻安全地跑。
13. 作为库的维护者，我想让研究子智能体在进度约三成时就把草稿落盘，以便被截断也留得下东西。
14. 作为库的维护者，我想给研究子智能体一个抓取次数上限，以便"越查越远"有终点。
15. 作为库的维护者，我想让主控在派完子智能体后回读产物（文件存在且非空），以便"完成"是验证过的而不是声称的。
16. 作为库的维护者，我想让只读命令（`git status`、列目录、检索）不再逐条确认，以便调查不被打断几十次。
17. 作为库的维护者，我想让已信任的文档域名连"内容入上下文"也自动批准，以便研究任务不再每抓一次问一次。
18. 作为库的维护者，我想让危险命令（删除、下载、改权限）继续要确认，以便自动批准不变成安全漏洞。
19. 作为库的维护者，我想随时看清 agent 当前在跑什么工具、进展到哪，以便"不知道在干什么"不再发生。
20. 作为库的维护者，我想在出事时能从调试日志回收子智能体的产出，以便一次事故不至于颗粒无收。

## 实现决策

**检查入口**

- 唯一入口是一个**单文件、零依赖**的 Node 脚本；不建 `package.json`、不装依赖、不加构建步骤。
- 退出码二值：全绿 0，任一失败 1。**不区分警告与错误**——机械项没有"差不多"。
- 只读：脚本不得写任何文件（红证用一次性临时目录，跑完即弃）。
- 输出约定：每条失败点名叫**文件路径 + 具体原因**；全绿时只打一行总结（避免噪声）。

**检查项分三批**（按"值不值得为它写检查"排序）

1. 结构性、零歧义：UTF-8 无 BOM；frontmatter `name` = 目录名；同目录兄弟 md 链接可解析。
2. 跨文件引用：技能正文里的跨技能引用指向真实存在的技能；技能目录数、README 表行数、地图状态行、移植表的数字互相一致（**数字由脚本从磁盘算**，不复述文档结论）。
3. 地图与切片的边界：决策票的 `类型` 取值限于 `research | prototype | grilling | task`，`状态` 限于 `待办 | 已认领 | 已解决 | 已关闭`，`阻塞于` 里的编号指向存在的票，地图「已定决策」的链接目标存在；切片只住在 `docs/workflow/specs/<slug>/slices/`、带验收清单、不带 `类型` 行；决策票只住在 `docs/workflow/maps/<effort>/tickets/`、带 `类型` 行、不带验收清单。

**红证**

- 每条检查在完成时必须附一次"改坏 → 报红 → 改回 → 变绿"的记录（写进该 ticket 的验收，不留独立文档）。
- 只有"跑过一次没报错"不算完成——与 01 的结论一致：无法打脸的东西，等于没有。

**研究防丢**

- `cwl-research` 增加三条：**先写盘**（约三成进度时落草稿，之后原地补写）、**抓取预算**（单子写明上限）、**回报含产物路径与行数**。
- `cwl-wayfinder` 的研究票模板增加一条：主控派单时必须写预算，并要求子智能体返回"路径 + 行数"；主控**回读验证**后才算解决。

**环境加固**

- 终端自动批准：只放行**只读**命令模式；写入、删除、下载类保持需要确认。
- URL 自动批准：对已信任的文档站，请求与响应两步都放开；其余域保持两步都问。
- 进度可见：开启持续进度显示，工具调用全程可见。
- 这些是**用户级设置**，不在版本库内；spec 只留决策，实际改动在设置里。

**落点纪律**

- 新建仓库根的 `AGENTS.md`，只放**导航指引 + 硬纪律**（不复制技能正文）：终端先合并再跑、临时文件写仓内暂存区、派子智能体先报备预算、说"完成"前回读证据。
- README 增加一行："怎么跑检查"。不写进 README 表格里（那里是技能清单，不是操作手册）。

## 测试决策

- **什么算好测试**：二值。同一份输入，要么绿要么红；断言只看两件事——退出码，以及失败输出里是否点名了那个文件。不测函数结构、不测文案格式。
- **被测的模块**：只有那个检查入口脚本。技能正文、`AGENTS.md` 是散文，不进自动测试——它们的质量靠人读，伪装成检查只会制造假安全感。
- **红证的做法**：复制一份最小坏样本（一个带 BOM 的文件、一个 name 不匹配的目录、一个断链、一张非法状态的票）到临时目录，断言报红；再对真实仓库断言全绿。
- **先例**：本仓库目前零检查，无先例。形态先例取自 `docs/attempts/01-codeview.md` §1.2 / §3.3 的六条机械关卡与红证做法——那是上次实验里**唯一稳定发挥作用**的部分。
- **不测的**：研究技能改动、`AGENTS.md` 落点、设置变更。这三者用一个可观察的行为验收（草稿是否中途存在、弹窗数是否下降），不写成自动化测试。

## 超出范围

- 读码陪读那条线（`docs/workflow/maps/reading-companion/` 的 03–07）：本 spec 不涉及，按地图推进。
- 两个暂缓技能（`wizard`、`to-questionnaire`）。
- 引入 CI、pre-commit hook、GitHub Actions：条件未到，单人单机手跑即可。
- 任何渲染器、HTML 报告、可视化工具。
- 技能内容的重译或大改：只做本文列出的最小改动。
- 上游技能的新一轮移植。

## 补充说明

- **一次决定的翻转**：2026-10-17 的复盘曾把"根 `AGENTS.md`"判为"先别动"。本 spec 显式重启它，理由是此后出现了新证据（52 分钟零落盘、几十次权限确认）。旧判定不是错的，只是当时的证据不足。
- **权限设置的位置**：用户级 `settings.json`，跨仓库生效，因此不进版本库，也不作为 ticket 的验收项；它的验收是行为观察（连续三条只读命令零确认）。
- **能力边界**：检查只能兜住机械项。技能写得对不对、触发面合不合适，仍然只能靠人读——不要因为有了检查就假设内容没问题。
- **红证的成本**：每条检查都要付一次"故意改坏"的成本。这是刻意的：01 证明了没有红证的关卡会悄悄失效。

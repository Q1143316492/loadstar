**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

实现的时候，注意力在「让它跑起来」上。跑起来之后，代码里会留下一层实现过程的痕迹：解释刚做了什么、给一段代码起个横幅、留着不用的旧版本、为绕过某个问题写长篇说明、函数长到一次读不完。这些在当下帮过忙，之后就成了读者要逐条读过去才能找到活代码的沉积。

这个技能在实现完成后跑一遍，把这一层削掉。

清单取自 Robert C. Martin 的 *Clean Code*，重叠度很高。读原书比读这份技能更彻底。

## 范围

用户指定的文件或 diff。没指定时用当前改动：`git diff` 加未跟踪文件。

## 三种处理方式

每一条痕迹都归入下面三类之一，没有第四类。

**直接做**：改的是文本，代码形状不变。删注释、删死代码、调空行。做完接着看下一条。

**MUST KILL**：要消掉它，唯一的办法是改代码形状——重命名、提取、加类型、改签名。**标出来，停下告诉用户**，给出位置和它暗示的重构。改不改由用户定。

**走开**：改动会改变行为。停下来报告，一个字都不动。

判断法：删掉之后还能编译、测试还能过的，属于第一类；不能的，看是形状变了还是行为变了。

`IMPORTANT`、`do not remove`、`太脆弱`、`暂时这样` 是气味不是证据。判定前先读附近的代码；仍然看不出来的，追那个符号的调用方。证不出属于放行清单的，删。

## 规则一：注释

**默认状态是没有注释。** 一条注释要留下来，得说清它守的是下面哪一类外部约束。

放行清单：

- 法律或版权头。
- 外部依赖、平台、协议强制的非显然行为：读代码看不出来，换写法也改不掉。
- 公共 API 的契约说明。
- 指向 issue 或 RFC 的链接。
- lint 或格式抑制，且被抑制的规则本身有缺陷。

五类都不沾的注释，属于下面四种形状之一：

| 形状 | 长什么样 |
|---|---|
| 叙述 | `// 先检查 X，再处理 Y`，而后面几行已经这么写了 |
| 横幅 | `// ===== 工具函数 =====`，而文件结构已经说明了 |
| 注释掉的尸体 | 整段被注释掉的旧实现 |
| 变通说教 | 三行以上解释「为什么这样绕」 |

两种另算，不是删而是 MUST KILL：

- 注释在解释**变量名该说的事** → 重命名。
- 注释在解释**这段代码为什么绕** → 提取或重新设计。

一条注释比它注释的代码还长，默认按变通说教处理。

文档注释（docstring、JSDoc、XML doc 之类）是代码的一部分：它可能进运行时反射、被文档生成抓走、是测试的来源。删之前确认没有人在读它。

## 规则二：其余痕迹

下面每一行都是「怎么认」加分类。同一段代码同时中了几条，就按最严重的那条处理。

### 重复

| 怎么认 | 处理 |
|---|---|
| 同一段逻辑出现两次以上，改一处要同步改另一处 | 同一文件内：直接合并。跨文件或跨模块：MUST KILL |
| 两个分支几乎相同，只有参数不同 | MUST KILL（参数化或提取） |
| 手工维护的列表与另一处的列表必须保持一致 | MUST KILL（改成单一事实源） |

### 死代码与杂物

| 怎么认 | 处理 |
|---|---|
| 被注释掉的整段代码 | 直接删 |
| 没有任何调用者的函数、类、字段、常量 | 直接删 |
| 未使用的 import、变量、参数 | 直接删 |
| 调试用的打印、临时日志、`TODO` 之外的占位代码 | 直接删 |
| 恒为真的条件、恒走不到的分支 | 直接删 |
| 只转发、没有任何独立价值的薄封装 | 直接删（把调用方指向被封装物） |
| 空的 `catch`、什么都不做的错误处理 | 走开 |
| 有返回值却从不处理 | 走开 |

### 命名

| 怎么认 | 处理 |
|---|---|
| 名字没说出意图：`data`、`info`、`temp`、`handle`、`process`、`result` | MUST KILL |
| 同一个概念在代码里用了两个名字 | MUST KILL |
| 同一个名字指代了两个概念 | MUST KILL |
| 名字带类型编码：`strName`、`iCount`、`arrItems` | MUST KILL |
| 布尔变量用否定名：`notReady`、`disabled` | MUST KILL |
| 名字需要注释来解释 | MUST KILL |

### 函数

| 怎么认 | 处理 |
|---|---|
| 一次读不完，或者要做的事不止一件 | MUST KILL（提取） |
| 参数超过三个 | MUST KILL |
| 用布尔 flag 参数切换两种行为 | MUST KILL（拆成两个函数） |
| 有输出参数，靠它把结果带出去 | MUST KILL（改成返回值） |
| 高层调度与底层细节写在同一函数里 | MUST KILL |
| 名字看不出来的副作用（写文件、改全局状态） | MUST KILL |

### 控制流与嵌套

| 怎么认 | 处理 |
|---|---|
| 嵌套超过两层 | MUST KILL（提前返回或提取） |
| 深缩进可以靠卫语句压平 | MUST KILL |
| 一行里塞了多个语句、多个赋值 | 直接拆成多行 |
| 布尔表达式长到需要读两遍 | MUST KILL（提取成有名字的谓词） |

### 魔法值

| 怎么认 | 处理 |
|---|---|
| 裸数字出现在逻辑里：超时、阈值、重试次数、端口、上限 | MUST KILL（提取具名常量） |
| 裸字符串当状态或键用：`"pending"`、`"user_id"` | MUST KILL（常量或枚举） |
| 重复出现的同一个字面量 | MUST KILL |
| `0`、`1`、`""`、循环起点这类自明的值 | 留 |

### 错误处理

| 怎么认 | 处理 |
|---|---|
| 用返回 `null`、`-1`、错误码表示失败 | MUST KILL（异常或 Result 类型） |
| 抛出的异常类型说不清出了什么事 | MUST KILL |
| 捕获了却吞掉 | 走开 |
| 统一入口却各自处理错误 | MUST KILL |

### 格式与结构

| 怎么认 | 处理 |
|---|---|
| 连续三行以上的空行 | 直接删空行 |
| 一行超过项目约定的宽度 | 直接折行 |
| 变量声明离它第一次使用隔了很多行 | MUST KILL（把声明移到使用处） |
| 一个文件里放了多个不相关的类或一组不相关函数 | MUST KILL（拆分） |
| 类的职责不止一个，改它有两个理由 | MUST KILL |

类的职责怎么划、模块边界怎么定、依赖方向怎么管，超出本技能：那是 `cwl-correct` 与 `cwl-codebase-design` 的事。

## 验证：全部改完，最后跑一次

**改的过程中不跑。** 这一轮的改动都只是删字符或调格式，逐条验证会让验证成本乘以条数，而收益是零。全部改完之后跑一次项目的 lint、编译和测试，把输出贴出来。

这一条是本技能的省时设计，不是省略步骤：**一次改完，一次验证**。

如果删除之后验证失败，说明那条注释或那段代码有承载物（被反射读到、被文档生成抓走、是测试的来源）。把那次删除恢复，在报告里说明。

## 报告

- 直接做的：几条，落在哪些文件。
- MUST KILL：位置，一句为什么它需要动代码形状，以及建议的重构。
- 走开的：位置，一句为什么它改的是行为。
- 勉强留下的注释：哪几条，守的是哪一类约束。
- 最后那次验证的输出。

**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

**只评审、只报告。** 不提交、不暂存、不改动仓库里的任何文件，也不执行会改变仓库状态的 git 操作（如 `fetch`）；git 只用于评审必需的只读查询——`git diff`、`git log`、`git rev-parse`。改什么、怎么改，由用户看过报告后决定。

一次评审走五步：**定范围** → **备材料** → **派两个子智能体** → **主审过滤** → **呈现并另存**。前两步攒材料，中间一步分头查，后两步收口。

两轴分开贯穿这五步，因为任何一条轴都能掩盖另一条：遵守每条标准却做错了东西，或做对了东西却破坏了项目约定，都只有在这种分离下才暴露出来。所以同一份 diff 派给两个子智能体查不同的事（第 3 步），过滤时不按一轴去重排另一轴（第 4 步），呈现时也不合并（第 5 步）。

## 流程

### 1. 锁定固定点

用户说的固定点是什么就是什么（commit SHA、分支名、tag、`main`、`HEAD~5`）。没指定就先问。

记下 diff 命令，三种形态：

- **已提交的改动**（默认）：`git diff <固定点>...HEAD`（三点写法，以 merge-base 为基准），配 `git log <固定点>..HEAD --oneline` 取提交列表。
- **含未提交的改动**：`git diff --merge-base <固定点>`，一直覆盖到工作区；只评审未提交部分时固定点取 `HEAD`。
- **用户直接给出一段 diff**：评审那段，跳过固定点推导，报告里注明来源。

前两种先确认固定点能解析（`git rev-parse`）且 diff 非空——坏的 ref 或空 diff 在这里失败，而不是在两个子智能体内部失败。

### 2. 备齐两轴的材料

**Spec**，按序找：

1. 用户传入的路径。
2. `docs/workflow/spec-lite/` 下与本次任务对应的那份一次性清单（`cwl-direct` 开工时写的）。
3. `docs/workflow/specs/` 下与分支名或功能名匹配的 spec。
4. 提交信息里引用的 issue / spec（`#123`、`Closes #45`）——取得到就取，取不到就跳过。

只看 `docs/workflow/`，不到其它子目录、仓库根或 `.scratch/` 里翻。

都没有时，把用户这次的需求整理成一份短清单（要做什么 / 怎么验收），请用户确认后再用，并注明 spec 由对话整理而来。连明确的需求都没有时停下来：这次评审只能查风格，判断不了做的是不是想要的东西，请用户先补 `spec-lite` 或说清需求。

**意图**：用一段话写清这次改动想做成什么，取自 spec、提交信息与对话，填进两份提示的 `{INTENT}`。拿不准就先问用户——评审者不质疑意图，只挑执行，意图错了整份评审都跟着偏。

**标准**：`docs/workflow/` 下的 `CODING_STANDARDS.md` 与同目录同类文档，加上仓库根的 `CONTRIBUTING.md`（若存在）。仓库没有标准文件就跳过这一层——标准是项目自己的事，不在评审时凭空立一套，报告里注明「本仓库尚无编码标准」。

个人品味、评审镜头、提示模板、发现的格式都在 [`REVIEWER.md`](REVIEWER.md)，与具体项目无关，不必另找。

### 3. 派两个子智能体

按 [`REVIEWER.md`](REVIEWER.md) 的「提示模板」拼两份提示，**同时发出、放在前台**，然后汇总两份报告：

- **标准子智能体**：`{DIFF_CMD}`、`{COMMITS}`、`{INTENT}` 照填；`{MATERIAL}` 填第 2 步的标准文件清单，外加与本技能同目录的 `REVIEWER.md` 路径——子智能体自己会读文件，整份贴进提示只是把 190 行搬进你的上下文；`{AXIS_BRIEF}` 用「标准轴」那段。
- **Spec 子智能体**：`{DIFF_CMD}`、`{COMMITS}`、`{INTENT}` 同上；`{MATERIAL}` 填 spec 的路径或已取回的内容；`{AXIS_BRIEF}` 用「Spec 轴」那段。让它只读「提示模板」与「Spec 轴」两段——品味与镜头属于标准轴的判断范围。

### 4. 过滤

先核对覆盖面：把 `git diff --name-only` 与标准子智能体报告末尾「看过的文件」对上，没对上的自己补看，补看得到的发现同样要过滤；补不了就记下这几个文件名，第 5 步末尾交代。

子智能体只看到 diff 的一个切片，完整上下文在你手里。逐条复核，在每条发现下补一行 `处理：`。四条只有你能判的：

- **假设 vs 实际**：「万一有人传 null」只有在调用点真能传进 null 时才算发现。追调用链——上游校验过、类型系统拦住了，就驳回。
- **我会换一种写法**：说不出当前写法具体坏在哪，只是偏好不同。驳回，并说清差别不在对错。
- **为第二处变化而抽象**：代码没有第二种改法时，提函数、加接口都是过早抽象。
- **缺上下文的信号**：标出了仓库里到处都在用的写法；要改作者根本没动过的代码；与你知道的约束冲突。这些是评审者只看到切片而误判，从容驳回。

严重度按后果类别复核，不按缺陷大小（三档定义见 `REVIEWER.md`「发现的格式」）：证据栏只有复述、给不出后果的，降级；连 `一般` 都够不上的，驳回。

处理结果四档：

- `动手` —— 该修。
- `考虑` —— 站得住，但成本与收益的账你不确定，把取舍摆给用户。
- `记下` —— 成立但没有可执行的动作（取决于本阶段之外的上下文，或此刻修不划算）。留在报告里占位，别让它冒充成「考虑」。
- `驳回` —— 错的、缺上下文的，或只是偏好。**理由必须写**，用户不认同你的判断时可以据此推翻。

**别把过滤做成单向的下压。** 评审者的价值正在于它不受你的先入之见牵制，所以驳回要付代价：

- 它指出的是一条具体的执行路径，不是假设
- 它让你发现自己对这块代码的心智模型有缺口
- 读完之后你想的是「……对，确实」
- 正确性与安全的问题，哪怕只有一条，也要多看一眼再驳

`动手` 超过 5 条，多半是没滤够。

**完成判据**：每条发现都带了 `处理：`，且每一档 `驳回` 都写了理由。

### 5. 呈现与另存

报告开头写一段 `## 意图`（第 2 步写的那个），然后两份报告分别放在 `## 标准` 与 `## Spec` 标题下，发现按 `REVIEWER.md`「发现的格式」照录。

整份报告全是风格偏好、没有实打实的问题时，直说代码站得住。Spec 轴被跳过时写明「无可用 spec」与原因，不从代码里倒推要求。第 4 步有没覆盖到的文件时，在末尾写明是哪几个。

最后用一行总结收尾：每条轴的发现总数，以及各轴内部最严重的问题（如有）。

**另存**：同一份报告写成 Markdown，放到 `$TMPDIR`（没有就用 `/tmp`，Windows 上是 `%TEMP%`），文件名 `<tmpdir>/code-review-<时间戳>.md`，每次运行一个新文件，仓库里不落任何文件。最后把绝对路径给用户。

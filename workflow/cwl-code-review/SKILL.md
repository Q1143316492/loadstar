对固定点与当前状态之间的 diff 做两条轴的评审：

- **标准（Standards）**：代码是否符合本仓库文档化的编码标准与用户的个人风格（后者主观，仓库优先）？
- **Spec**：代码是否忠实实现了起源 issue / spec？

两条轴都作为**并行子智能体**运行，避免互相污染上下文，然后由本技能汇总它们的发现。

不提交、不暂存、不执行任何会改变仓库状态的 git 操作（如 `fetch`）。git 的使用仅限评审必需的只读查询——`git diff`、`git log`、`git rev-parse`。

## 流程

### 1. 锁定固定点

用户说的固定点是什么就是什么（一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等）。没指定就先问。

按要评审的对象记下 diff 命令，三种形态：

- **已提交的改动**（默认）：`git diff <fixed-point>...HEAD`（三点写法，比较基准是 merge-base）。同时用 `git log <fixed-point>..HEAD --oneline` 记下提交列表。
- **含未提交的改动**：`git diff --merge-base <fixed-point>`——以 merge-base 为基准、一直覆盖到工作区（含已暂存与未暂存的改动）。只想评审未提交的改动时，固定点取 `HEAD`。
- **用户直接给出的一段 diff**：就评审那段 diff，跳过固定点推导；报告里注明它由用户提供。

对前两种形态，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空——坏的 ref 或空 diff 应该在这里失败，而不是在两个并行子智能体内部失败。

### 2. 确定 spec 来源

按这个顺序找起源 spec：

1. 用户作为参数传入的路径。
2. 提交信息里引用到的 issue / spec（`#123`、`Closes #45` 等）——能直接取回就取回（比如引用指向仓库内的文件）；取不回就跳过。
3. `docs/`、`specs/`、`openspec/changes/` 或 `.scratch/` 下、与分支名或功能名匹配的 spec 文件。
4. 都没找到，就问用户 spec 在哪里。如果用户说没有，**Spec** 子智能体跳过并报告 "no spec available"。

### 3. 确定标准来源

搜遍仓库里每一份记录「代码该怎么写」的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时，它必须在清单上。

在仓库已记录的内容之上，标准轴始终携带下面的**气味基线（smell baseline）**：一组固定的 Fowler 代码坏味道（_Refactoring_，第 3 章），即使仓库什么都没记录也适用。两条规则约束它：

- **仓库优先。** 文档化的仓库标准总是胜出；它认可某件基线会标记的做法时，压制该坏味道。
- **永远是主观判断。** 每条坏味道都是带标签的启发式提示（"possible Feature Envy"），绝不是硬性违规。和这里的任何标准一样，工具已经强制的都跳过。

每条坏味道的读法是 *它是什么* → *怎么修*；拿它与 diff 对照：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字看不出它做什么、存什么。→ 重命名它；想不出诚实的名字，说明设计本身混沌。
- **重复代码（Duplicated Code）**：同一个逻辑形状在这次改动中出现于不止一个 hunk 或文件。→ 抽出共享形状，两处都调用它。
- **特性依恋（Feature Envy）**：一个方法访问另一个对象的数据比访问自己的还多。→ 把该方法搬到它所依恋的数据上。
- **数据泥团（Data Clumps）**：同样的几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 打包成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用一个基本类型或字符串代表值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：同一个类型上的同一套 `switch`/`if` 级联在改动中反复出现。→ 换成多态，或两处共享一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑改动迫使 diff 里许多文件出现零散编辑。→ 把一起变化的东西聚到一个模块里。
- **发散式变化（Divergent Change）**：一个文件或模块因为若干互不相关的原因被编辑。→ 拆分，让每个模块只因一个原因而变化。
- **夸夸其谈通用性（Speculative Generality）**：为 spec 并不存在的需求添加的抽象、参数或钩子。→ 删掉它；先内联回去，等真实需求出现再说。
- **消息链（Message Chains）**：调用方不该依赖的长链 `a.b().c().d()` 导航。→ 把这串链式导航藏在第一个对象的一个方法后面。
- **中间人（Middle Man）**：一个类或函数大部分只是在往下委托。→ 砍掉它，直接调用真正的目标。
- **被拒绝的馈赠（Refused Bequest）**：一个子类或实现者忽略或覆盖了它继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 先修正，再并行评审

先派**修正子智能体**：给它 diff 命令与 [AUTO-FIX.md](AUTO-FIX.md)、[ASK-FIRST.md](ASK-FIRST.md) 全文，让它逐 hunk 检查 diff 触及的行——按 AUTO-FIX.md 直接改，按 ASK-FIRST.md 只列出来。返回「已改 N 处（文件:行）」与待问清单。

再**并行**派出标准与 Spec 两个子智能体（调用同时发出、放在前台），评审修正后的树，然后汇总它们的报告。

**标准子智能体的提示词**应包含：

- 完整的 diff 命令和提交列表。
- 第 3 步找到的标准来源文件清单，**外加第 3 步的气味基线全文粘贴**（该子智能体没有其他途径拿到它）。
- 简报："逐文件、逐 hunk 报告：(a) diff 中每一处违反文档化标准的地方，引用标准出处（文件 + 规则）；(b) 你发现的每一条基线坏味道：报出名称并引用所在 hunk。区分硬性违规与主观判断：文档化标准的违反可以算硬性，基线坏味道永远是主观判断，且文档化的仓库标准覆盖基线。工具已经强制的跳过。400 字以内。"

**Spec 子智能体的提示词**应包含：

- diff 命令和提交列表。
- spec 的路径或已取回的内容。
- 简报："报告：(a) spec 要求但缺失或只做了一半的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看起来实现了、但实现有误的需求。每条发现都引用对应的 spec 原文。400 字以内。"

如果 spec 缺失，跳过 Spec 子智能体，并在最终报告中注明。

### 5. 汇总

把两份报告分别放在 `## 标准` 与 `## Spec` 标题下呈现，逐字照录或稍作清理。**不要**合并或重排发现：两条轴是刻意分开的（见 _为什么是两条轴_）。修正子智能体的「已改 N 处」附在标准轴末尾；它的待问清单单列一节 `## 风格（待你决定）`，没有就省略。

最后用一行总结收尾：每条轴的发现总数，以及每条轴内部最严重的问题（如有）。不要跨轴挑出唯一赢家：那正是这种分离要防止的重排。

## 为什么是两条轴

一个改动可以过一条轴而挂另一条：

- 遵守每一条标准、但实现了错误东西的代码 → **标准过，Spec 挂。**
- 完全做到了 issue 要求的事、但破坏了项目约定的代码 → **Spec 过，标准挂。**

分开报告，才能阻止一条轴掩盖另一条。

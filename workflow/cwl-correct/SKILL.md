**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

操作者一直在为**同样的错误**反复纠正这个仓库里的 agent。要改的是仓库，让下一个 agent**做不出**这个错误。

假定每个贡献者都是一个 agent：它只看得见自己打开过的文件，会抄最近的那个例子，会走「能编译通过」的最短路。把仓库设计成：**从单个文件看是对的改动，对整个仓库也是对的。**

## 找出错误类别

先读最近的提交、回滚、评审意见、agent 指令文件，以及那些在解释变通做法的注释。把错误归成类。**一类错误发生过两次，才算一类。**

## 用能起作用的最高层级修掉每一类

1. **用架构消除它。** 每份状态只有一个所有者，每个任务只有一条受支持的做法。把内部藏起来，让错误的 import 直接失败。用单一事实源取代需要手工同步的列表。删掉旧做法和 agent 会去抄的死代码。
2. **用类型强制它，让坏状态写不出来。** 如果坏代码仍然能编译，就加一条 lint 或 CI 检查，并让它的报错写明该改用哪个文件、哪个类型、哪个函数。如果这个写法已经很普遍，就只在改动新增了这类写法时才失败。
3. **测试行为。** 修掉或删掉那些「被检查的行为坏了它却还是绿的」测试，或者「只改了内部实现它就变红」的测试。
4. **条件和判断类的事，才写文档或 agent 规则，而且放最后。** agent 跳过它们的时候，什么都不会报错。

## 修掉并证明

然后现在就修掉最频繁的那几类，**一次提交只修一类**。每条新检查都要**在一条真实的历史错误上证明它会失败**。本地和 CI 跑同一条命令。例外要写在出问题的那一行上，带上理由、失效日期，和一个人的批准。

## 维护规则表

最后，在 agent 指令文件里维护一张表，把**每条规则**和**执行它的东西**配对。操作者纠正你的时候：修掉错误，并加上这条规则。如果规则本来就在、却没有任何东西执行它，那说明这是重复犯错——**在同一次改动里用最高层级修掉它**。一旦某条规则对应的错误已经不可能发生，就把这条规则删掉。

**回复时：** 每一类给出它的证据、你选的层级，以及为什么更高的层级行不通。

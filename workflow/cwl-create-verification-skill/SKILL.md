**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

每个认真的项目都需要一条脚本化的办法来驱动真实应用并证明行为：启动它、像用户那样用一遍某个功能、把证据抓下来。这个技能把这套东西生成为一个项目本地技能（`docs/workflow/verify/<名字>/`），按这个仓库的情况裁剪。你写的产物是给**下一个 agent** 看的，不是给人：它会中途接手、冷读、从没见过这个应用。

## 1. 采访仓库，不是采访用户

从代码库里回答这些问题，只有观察不到的才问用户：

- **Surface**：用户实际碰到的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用、库？一个仓库可以有好几个，挑主要的那个，其余记下来。
- **Run**：本地怎么启动？优先用仓库自己文档里的 dev 命令（package 脚本、Makefile、README 快速启动）。记下端口、环境变量、种子数据、鉴权。
- **Drive**：agent 怎么用程序化方式跟它交互？**先找已有的 harness**——Playwright/Cypress 规格、expect 脚本、PTY 助手、可 curl 的端点、调试端口。然后才挑通用配方：web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY，服务用纯 HTTP。
- **Observe**：能抓到什么证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **Isolate**：两个实例能并排跑吗（端口、数据目录、profile）？不能时，在生成的技能里写明：拒绝双重驱动一个共享实例，好过损坏用户的会话。

检出代码按原样构建或启动不了时，先修好它（或者精确地报告），再生成；针对坏底座写出来的技能教的是错的步骤。当一个无关的缺件挡住启动时（API 从不会提供服务的静态目录、示例配置），生成的技能可以创建它，明确标注为验证脚手架，并在清理时移除。

## 2. 生成技能

写 `docs/workflow/verify/<名字>/SKILL.md`，带 YAML frontmatter（`name: verify-<名字>`，以及一个 description：点名这个应用、它的 surface、什么时候该取用它——没有 frontmatter 技能不会注册），以及下面这些节，每一节都落在采访实际找到的东西上（不留占位符）：

- **Launch**：为验证启动应用的确切命令，以及怎么判断它准备好了（一行日志、一个提示符）。Launch 必须从空数据目录到达可用状态，包括迁移和种子数据。**就绪意味着可用，不是进程应答了**。数据库健康检查能通过，而它的初始化脚本还在跑。包含拆卸。短命的 CLI 或 TUI 没有要保持活着的服务：launch 指的是构建一次（或装依赖），然后每次驱动都在自己的独立 PTY 或 tmux 会话里开始。
- **Doctor**：一个只读检查，回答「这个实例值得驱动吗」——进程在跑、版本/构建对、端口是我们的、凭据有效。任何东西看起来不对劲时，agent 先跑它。
- **Drive**：带着这个仓库真实选择器和命令的驱动配方，不是示例。优先用稳定的把手（ARIA 标签、data 属性、提示符字符串、路由路径），而不是坐标和 tab 顺序。
- **Evidence**：为一次证明抓什么、抓到哪里。写明证明标准：走真实用户路径，不用内部 setter 或测试专用端点；抓动作和它造成的结果状态，不只抓最后一屏；验证副作用（写出的文件、插入的行、发出的消息），和可见的东西一起；只在该生产边界已经隔离了外部系统的地方用 mock。当安全路径是 dry-run 或测试模式时，**通过观察确认它实际跳过了什么**（文件、网络、git refs），而不是相信它的名字：有些 dry-run 仍然会碰网络或打开浏览器。
- **Cleanup**：怎么拆掉这次运行创建的实例。按进程名杀进程不行，杀你自己启动的那个。清理移除实例和临时状态，绝不移除证据：证明产物要活过拆卸，放在技能点名的位置。
- **Helpers**：技能附带的脚本是可执行的，它的调用方式写在技能正文里。一个要读者自己逆向的 helper 不算 helper。

## 3. 播种功能地图

创建 `docs/workflow/verify/<名字>/features/README.md`，外加一个用户可见功能一个文件（先写你能识别出的前 3–5 个，从路由、命令、菜单或文档里找）。按 [`references/feature-map-format.md`](references/feature-map-format.md) 里的形状写，一个 README 索引加一个功能一个文件。每个文件从用户视角回答：这个功能是什么、怎么到达它、怎么用这个 harness 驱动它、什么可观测的终态能证明它能用。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas`。

种子数据缺少某个 journey 需要的前置条件时，那个 journey 报失败，原因写进那个功能的 `Gotchas`。**绝不放宽 journey 让它通过。** 地图是这个仓库维护中的验证事实源；当地图上列了多个入口时，只驱动了一个方便入口的证明是不完整的。

## 4. 交付前先证明生成的技能

照着它自己的说明端到端跑一次：启动、体检、驱动**一个**已映射的功能（一个就够；地图存在就是为了让后续运行覆盖其余）、抓证据、清理。清理之后确认证据还在它被点名的位置——把证明吃掉的清理，这一步算失败。失败的地方修好，并且每次失败的迭代之后也跑一遍生成的清理，免得坏尝试留下进程和端口。**从没被执行过的生成技能是草稿，不是交付物。** 如果你是在真实目标的替身里证明的（容器代替全新的 VM、本地栈代替远端），列出替身做过的、真实目标不会做的每一步。那些步骤在真实目标上跑过之前，保持未验证状态。

## 5. 交接保养循环

把用户指向 [`cwl-maintain-verification-skill`](../cwl-maintain-verification-skill/SKILL.md)，用来在应用变化时保持地图诚实。用户问起时才建议频率。

# 调试模式

**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

核心：**不要靠读代码猜运行时。先提可证伪的假设，再用日志取证，最后定点修复并清场。**

Cursor 的 Debug Mode 是产品内置模式，日志发给扩展里的本地调试服务器；本技能是可移植版，用**项目内一个专用的日志目录**代替那个服务器。

## 何时用

- 能复现，但读代码看不出原因
- 竞态、时序、异步顺序问题
- 性能问题、内存泄漏：需要运行时测量
- 回归：以前是好的，现在坏了

## 何时不用

- 有调试器 / REPL 能停住：断点优先
- 已有现成的失败测试：直接跑它
- 读一眼就确定的问题（明显的空指针、拼错的路径）：直接修

判断标准：**答案是否取决于运行时才知道的值。** 是，就开这个模式。

## 阶段 1：探索并提假设

先建立上下文，再列假设：

- 读相关代码，画出执行路径。
- 写下**症状原话**，以及**预期 vs 实际**。
- 生成 **3–5 条**候选根因。只列一条会锚死在第一个看似合理的想法上。
- 每条都必须可证伪：「如果 X 是原因，日志里应该看到 Y；如果不是，应该看到 Z。」

说不出预测的假设是感觉，扔掉或磨锋利。没有具体假设就插桩，等于「全量打日志再 grep」——本技能明确禁止。

## 阶段 2：插桩

### 探针直接写文件

**探针自己写文件，不走项目 logger。** 项目运行日志动辄几万行，混进去 `rg` 出来全是噪音。

写到项目里的 `docs/workflow/cwl-debug/<run-id>.log`，追加写：

```text
dbg(event, **kv):
    以追加模式打开 <项目根>/docs/workflow/cwl-debug/<run-id>.log
    写入一行 [DEBUG-<run-id>] ts=... at=... event=... k=v k=v
    关闭文件
```

各语言写法不同（Python 的 `with open`、C# 的 `using`、C++ 的 `std::ofstream`），形状都是**打开、写一行、关闭**。不建日志框架，不注册 handler，不加依赖。

**零副作用原则：只加临时探针、只写这个目录。** 不新增配置、不动 `.gitignore`、不装依赖、不改构建脚本、不改日志配置。

**绝不打印密码、token、cookie、个人数据**；必须打就脱敏。

### 打在哪

- 函数入口与出口（参数、返回值）
- 分支选择（走的哪边）
- 外部调用前后（请求参数、响应摘要、耗时）
- 状态变更前后（改之前、改之后）
- 跨模块 / 跨进程的边界——最难猜的地方
- 性能 / 内存：计时、计数、分配量；不要写叙述性日志

不打：循环体内部（除非只打计数）、纯 getter、框架自己的噪音。

### 行格式

一行一个事件，固定字段，方便 grep，也方便肉眼扫：

```text
[DEBUG-<run-id>] ts=<ISO8601> at=<file:line> event=<名字> k=v k=v
```

```text
[DEBUG-a4f2] ts=2026-10-31T10:12:03.114 at=src/cache.ts:42 event=lookup key=user:7 hit=false
[DEBUG-a4f2] ts=2026-10-31T10:12:03.115 at=src/cache.ts:55 event=fill key=user:7 source=db rows=1
```

- `run-id` 用 4 位十六进制，每次会话一个，不要复用。
- 对象要序列化（JSON 或结构化字符串），不要 `str(obj)` / 默认 `toString()`——那正是要靠日志消除的猜测。
- 时间戳带毫秒：并发与时序问题全靠它。

### 前缀是清场的关键

所有探针都带 `[DEBUG-<run-id>]`。收尾时一行 grep 就能找全。**没打标签的日志会活下来，打了标签的必须死。**

## 阶段 3：复现（人在环）

复现由用户执行，你负责给步骤：

- 给出**具体、可执行**的复现步骤，不是「再试一次」。
- 让用户确认「预期发生什么 / 实际发生什么」。
- 时好时坏的问题：请用户重复多次，提高复现率。
- 等用户操作完，再读日志。

## 阶段 4：分析日志

只读本次的 `docs/workflow/cwl-debug/<run-id>.log`，不要到项目原有日志里翻。

- 先 `grep '\[DEBUG-<run-id>\]'`，再按 `event=` 过滤；不要把整个文件读进上下文。
- 引用**原文行**。报告里写「日志显示 `hit=false`」，不写「缓存可能没命中」。
- 描述运行时值只许引用日志，禁止「应该 / 可能 / 大概」。
- 日志里没有 = 探针没走到。这本身是信息，不要假设它「应该」打印了。
- 逐条标记假设：支持 / 推翻。被推翻的记下来，别悄悄丢掉。
- 信号不够就回阶段 2 加探针；每次只改一处。

## 阶段 5：定点修复

- 只改根因，通常几行。
- 不顺手重构、不扩大范围。
- 有条件的话，把日志里看到的症状固化成一条回归测试。

## 阶段 6：验证并清场（硬门）

- [ ] 按原步骤重跑复现（自己跑，或请用户再走一遍）
- [ ] 确认日志里的值真的变了、症状消失，而不是「看起来好了」
- [ ] 删掉所有带 `[DEBUG-<run-id>]` 的代码
- [ ] 删掉 `docs/workflow/cwl-debug/` 下的日志文件
- [ ] 临时改过的配置、依赖清单、构建脚本已原样恢复
- [ ] `grep -rn 'DEBUG-<run-id>' . --exclude-dir=.git --exclude-dir=node_modules` 结果为 0
- [ ] `git status` / `git diff` 里没有调试残留
- [ ] 报告写清楚：根因、日志里的哪一行证明了它、删了什么、恢复过什么

## 常见失败模式

| 症状 | 真正的问题 |
|---|---|
| 打了 50 条日志还是读不过来 | 没有阶段 1 的假设，在「全打再 grep」 |
| 日志全混在引擎 / 服务的运行日志里 | 探针走了项目 logger，改成自己写文件 |
| 改完「好像好了」 | 没重跑，没确认日志里的值真的变了 |
| 提交里混进了调试代码或日志 | 清场没当成硬门 |
| 为了调试装了新日志库 | 一个追加写就够，不需要框架 |
| 打印了 token | 泄露；立刻轮换，并在报告里说明 |

# 调试模式

**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

核心：**不要靠读代码猜运行时。先提可证伪的假设，再用日志取证，最后定点修复并清场。**

Cursor 的 Debug Mode 是产品内置模式，日志发给扩展里的本地调试服务器；本技能是可移植版，用**项目自己的日志通道**代替那个服务器——没有现成通道时，才落到一个最小的本地文件。

## 何时用

- 能复现，但读代码看不出原因
- 竞态、时序、异步顺序问题
- 性能问题、内存泄漏：需要运行时测量
- 回归：以前是好的，现在坏了

## 何时不用

- 有调试器 / REPL 能停住：断点优先
- 已有现成的失败测试：直接跑它
- 读一眼就确定的问题（明显的空指针、拼错的路径）：直接修

判断标准：**答案是否取决于运行时才知道的值。** 是，就开这个模式。

## 阶段 1：探索并提假设

先建立上下文，再列假设：

- 读相关代码，画出执行路径。
- 写下**症状原话**，以及**预期 vs 实际**。
- 生成 **3–5 条**候选根因。只列一条会锚死在第一个看似合理的想法上。
- 每条都必须可证伪：「如果 X 是原因，日志里应该看到 Y；如果不是，应该看到 Z。」

说不出预测的假设是感觉，扔掉或磨锋利。没有具体假设就插桩，等于「全量打日志再 grep」——本技能明确禁止。

## 阶段 2：插桩

### 先用项目自己的方式

**优先复用项目已有的日志设施**：现有 logger、引擎的日志 API、框架的 log facade、已有的日志目录与级别开关。遵循项目的日志格式、级别与脱敏规范。

- **不要为了调试引入第三方日志库。**
- 项目 logger 只写 stdout、而你看不到 stdout 时，先看它有没有文件 sink 或配置项；有就开，但记录改了哪个文件，清场时原样改回。
- 没有可用通道时，才写几行本地文件追加：不建抽象、不加依赖。

**零副作用原则：除了加临时探针和往仓外临时目录写日志，不修改任何其他文件。** 探针只加在本次复现路径经过的文件上，不顺手碰无关文件；不新增配置、不动 `.gitignore`、不装依赖、不改构建脚本。需要临时改项目配置才能开日志通道时，只改最小的一处，并在清场阶段原样恢复；如果改配置的影响面超出这次调试，改用仓外的本地文件追加。

### 写文件（仓外）

日志写到**系统临时目录**，不要写进仓库：

```text
<系统临时目录>/cwl-debug/<项目名>-<run-id>.log
```

系统临时目录用平台默认值（`$TMPDIR` / `%TEMP%`），不要在技能里硬编码 `/tmp`。

**不碰 `.gitignore`。** 日志不进仓，就不需要忽略规则；为了调试改版本控制配置本身就是副作用。

写文件的理由：长进程、后台服务、测试并发、游戏引擎——stdout 会被吞、被截断、被其他输出淹没；会话结束后 stdout 就没了，文件还在。每次运行一个文件，追加写。

**绝不打印密码、token、cookie、个人数据**；必须打就脱敏。

### 打在哪

- 函数入口与出口（参数、返回值）
- 分支选择（走的哪边）
- 外部调用前后（请求参数、响应摘要、耗时）
- 状态变更前后（改之前、改之后）
- 跨模块 / 跨进程的边界——最难猜的地方
- 性能 / 内存：计时、计数、分配量；不要写叙述性日志

不打：循环体内部（除非只打计数）、纯 getter、框架自己的噪音。

### 行格式

一行一个事件，固定字段，方便 grep，也方便肉眼扫：

```text
[DEBUG-<run-id>] ts=<ISO8601> at=<file:line> event=<名字> k=v k=v
```

```text
[DEBUG-a4f2] ts=2026-10-31T10:12:03.114 at=src/cache.ts:42 event=lookup key=user:7 hit=false
[DEBUG-a4f2] ts=2026-10-31T10:12:03.115 at=src/cache.ts:55 event=fill key=user:7 source=db rows=1
```

- `run-id` 用 4 位十六进制，每次会话一个，不要复用。
- 对象要序列化（JSON 或结构化字符串），不要 `str(obj)` / 默认 `toString()`——那正是要靠日志消除的猜测。
- 时间戳带毫秒：并发与时序问题全靠它。

### 前缀是清场的关键

所有探针都带 `[DEBUG-<run-id>]`。收尾时一行 grep 就能找全。**没打标签的日志会活下来，打了标签的必须死。**

## 阶段 3：复现（人在环）

复现由用户执行，你负责给步骤：

- 给出**具体、可执行**的复现步骤，不是「再试一次」。
- 让用户确认「预期发生什么 / 实际发生什么」。
- 时好时坏的问题：请用户重复多次，提高复现率。
- 等用户操作完，再读日志。

## 阶段 4：分析日志

- 先 `grep '\[DEBUG-<run-id>\]'`，再按 `event=` 过滤；不要把整个文件读进上下文。
- 引用**原文行**。报告里写「日志显示 `hit=false`」，不写「缓存可能没命中」。
- 描述运行时值只许引用日志，禁止「应该 / 可能 / 大概」。
- 日志里没有 = 探针没走到。这本身是信息，不要假设它「应该」打印了。
- 逐条标记假设：支持 / 推翻。被推翻的记下来，别悄悄丢掉。
- 信号不够就回阶段 2 加探针；每次只改一处。

## 阶段 5：定点修复

- 只改根因，通常几行。
- 不顺手重构、不扩大范围。
- 有条件的话，把日志里看到的症状固化成一条回归测试。

## 阶段 6：验证并清场（硬门）

- [ ] 按原步骤重跑复现（自己跑，或请用户再走一遍）
- [ ] 确认日志里的值真的变了、症状消失，而不是「看起来好了」
- [ ] 删掉所有带 `[DEBUG-<run-id>]` 的代码
- [ ] 删掉本次的临时日志文件与目录（都在仓外）
- [ ] 临时改过的配置、`.gitignore`、依赖清单、构建脚本已原样恢复
- [ ] `grep -rn 'DEBUG-<run-id>' . --exclude-dir=.git --exclude-dir=node_modules` 结果为 0
- [ ] `git status` / `git diff` 里没有调试残留
- [ ] 报告写清楚：根因、日志里的哪一行证明了它、删了什么、恢复过什么

**日志在仓外，本来就不会进提交。** 如果发现自己在仓内建了日志文件，删掉它，并确认 `.gitignore` 没被改过；不要用「把日志加进忽略」来收尾，那会把副作用留在仓库里。

## 常见失败模式

| 症状 | 真正的问题 |
|---|---|
| 打了 50 条日志还是读不过来 | 没有阶段 1 的假设，在「全打再 grep」 |
| 日志里全是框架噪音 | 打进了框架内部，挪回自己的边界 |
| 改完「好像好了」 | 没重跑，没确认日志里的值真的变了 |
| 提交里混进了调试代码 | 清场没当成硬门 |
| 为了调试装了新日志库 | 没先找项目已有的日志通道 |
| 改了 `.gitignore` / 配置来「方便调试」 | 副作用；日志该写仓外，配置该原样恢复 |
| 打印了 token | 泄露；立刻轮换，并在报告里说明 |

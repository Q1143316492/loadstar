# 诊断 bug

**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

一套对付疑难 bug 的纪律。除非有明确理由，不要跳过任何阶段。

探索代码库时，读 `docs/workflow/GLOSSARY.md`（如果存在），拿到相关模块的清晰心智模型；并检查你正在触碰区域的 ADR。

## 脱敏

本技能会让你展示命令、输出和捕获的产物。**先脱敏每一个秘密**：用 `<REDACTED>` 占位。反馈回路要基于环境变量搭建，让凭据留在环境里、而不是出现在你展示的东西里。捕获的产物带认证头：只引用承载信号的那几行。

脱敏后的输出不足以诊断这个 bug 时，直说，并问用户。

## 阶段 1：构建反馈回路

**这就是技能本身。** 其余都是机械劳动。只要你有这个 bug 的**紧的**通过/失败信号（一个在*这个* bug 上会打红的信号），原因一定能找到；二分、假设检验、插桩都只是消费它。如果没有，盯着代码看多久都救不了你。

在这里花不成比例的力气。**要凶、要创造性、拒绝放弃。**

### 构造它的方式，大致按这个顺序

1. **失败的测试**：在能触到 bug 的任何接缝上——单元、集成、e2e。
2. **Curl / HTTP 脚本**：对着运行中的 dev server 打。
3. **CLI 调用**：带一个固定输入，stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，对 DOM/console/网络做断言。
5. **重放捕获的轨迹。** 把真实的网络请求 / 载荷 / 事件日志存到磁盘，单独走一遍代码路径重放它。
6. **一次性 harness。** 起一个系统的最小子集（一个服务、mock 掉依赖），用一次函数调用就能走到 bug 的代码路径。
7. **属性 / fuzz 回路。** bug 是「输出有时不对」时，跑 1000 个随机输入找失败模式。
8. **二分 harness。** bug 出现在两个已知状态之间（提交、数据集、版本）时，把「在状态 X 启动、检查、重复」自动化，让 `git bisect run` 能跑它。
9. **差分回路。** 同一输入分别走旧版本与新版本（或两份配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。必须人来点时，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让回路仍然是有结构的。捕获的输出回传给你。

建对反馈回路，bug 就修好了 90%。

### 收紧回路

把回路当产品。一旦有了*一条*回路，就**收紧**它：

- 能更快吗？（缓存准备步骤、跳过无关初始化、缩小测试范围。）
- 信号能更利吗？（断言具体症状，而不是「没崩」。）
- 能更确定吗？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络。）

30 秒还时灵时不灵的回路比没有好不了多少；2 秒且确定的回路是紧的，是调试超能力。

### 时好时坏的 bug

目标不是干净的复现，而是**更高的复现率**。触发器循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。50% 抖动的 bug 可调，1% 的不可，所以持续拉高复现率直到可调。

### 确实造不出回路时

停下，明确说出来。列出你试过的东西。向用户要：(a) 能复现它的环境的访问权，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**没有回路，不许进入建假设环节。**

### 完成标准：一条紧的、能打红的回路

阶段 1 完成的条件是回路**紧**且**能打红**：你能说出**一条命令**（脚本路径、测试调用、curl），你**已经至少跑过它一次**（展示调用和输出，脱敏），并且它：

- [ ] **能打红**：驱动真正的 bug 代码路径，并断言**用户的精确症状**，所以它能在这个 bug 上打红、修好后转绿。不是「跑起来不报错」；它必须能*抓住这个具体的 bug*。
- [ ] **确定**：每次运行同一结论（时好时坏的 bug：按上文钉住一个高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可跑**：你能无人值守地跑它；人在环只经 `scripts/hitl-loop.template.sh`。

如果发现自己在命令存在之前就开始读代码建理论，**停：直接跳向假设正是这个技能要防的失败。** 没有能打红的命令，没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看着它在 bug 出现时打红。

确认：

- [ ] 回路产出的是**用户**描述的失败模式，而不是碰巧在附近的另一个失败。错的 bug = 错的修复。
- [ ] 失败在多次运行间可复现（时好时坏的 bug：以足够高的复现率可复现，以便对着它调试）。
- [ ] 你捕获了精确症状（错误消息、错误输出、慢的计时），让后续阶段能验证修复真的解决了它。

### 最小化

一旦它红了，把复现收缩到**仍然打红的最小场景**。输入、调用方、配置、数据、步骤**一次砍一个**，每砍一刀重跑回路，只留下对失败承重的东西。

为什么要费这个事：最小复现缩小阶段 3 的假设空间（可怀疑的活动部件更少），并且成为阶段 5 里干净的回归测试。

完成条件是**每一个剩下的元素都承重**：拿掉任何一个，回路就转绿。

复现**并**最小化之前，不要继续。

## 阶段 3：建假设

在测试任何一个之前，先产生 **3–5 条排序的假设**。单假设生成会锚死在第一个看似合理的想法上。

每条假设都必须**可证伪**：说出它做出的预测。

> 格式：「如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。」

说不出预测的假设是感觉：扔掉，或者磨锋利。

**测试之前，把排序的清单给用户看。** 他们常有瞬间重排的领域知识（「我们刚给第 3 条部署了改动」），或知道他们已经排除过的假设。便宜的检查点，巨大的省时。不要阻塞在这上面；用户不在就先按你的排序走。

## 阶段 4：插桩

每个探针都必须对应阶段 3 的一条具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**（环境支持的话）。一个断点胜过十条日志。
2. **定点日志**，打在能区分假设的边界上。
3. 绝不「全打日志再 grep」。

**给每条调试日志打标签**，用唯一前缀，例如 `[DEBUG-a4f2]`。收尾的清场变成一次 grep。没打标签的日志幸存，打了标签的死亡。

**性能分支。** 性能回归通常不该看日志。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**修复之前**先写回归测试——但只在存在**正确接缝**的前提下。

正确接缝，是测试能在其中复现调用现场发生的**真实 bug 模式**的接缝。如果唯一可用的接缝太浅（bug 需要多个调用方，却只有单调用方的测试；复现不了触发链的单元测试），写在那里的回归测试给的是虚假信心。

**没有正确接缝，这本身就是发现。** 记下来。代码库架构在阻止这个 bug 被锁死。把它标给下一个阶段。

存在正确接缝时：

1. 把最小化的复现变成那个接缝上的失败测试。
2. 看它失败。如果你是通过改代码或 fixture 强制的红，先与一份原始副本 `diff`，证明改动确实生效了，再信它。
3. 应用修复。
4. 看它通过。
5. 用阶段 1 的反馈回路重跑原始（没最小化的）场景。

## 阶段 6：清场

宣布完成之前，必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者「没有接缝」已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 那个前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 纠正过来的那条假设写进了提交信息，让下一个调试者学到

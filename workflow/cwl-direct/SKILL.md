# 一次做到位

范围已经明确，读完项目约定就动手，细节边做边定。交付的是**正式实现**：一路推进到用户能直接拿去用的状态，并用一个最小视图把这次动到的路径讲清楚。

## 动手前：读项目约定

动手之前先把这些读完，按顺序，存在才读：

1. 项目根的 `CLAUDE.md` / `AGENTS.md`。
2. `docs/workflow/AGENTS.md` —— 本项目的工作流约定，写明了哪些是硬规矩。
3. `docs/workflow/CODING_STANDARDS.md` 或其他编码标准文档。
4. 项目偏好 `docs/workflow/PREFERENCES.md`（没有就看项目根的）：格式见 [PREFERENCES-FORMAT.md](PREFERENCES-FORMAT.md)。

优先级：**用户这条消息 > 项目硬规则 > `PREFERENCES.md` > 本技能默认**。

## 开工前：写一份一次性清单

在 `docs/workflow/spec-lite/<任务slug>.md` 写两个小节：`## 要做`（这次交付的范围）和 `## 验收`（怎么确认做完了）。每条一句话，验收条目要能直接观察——写「断网后消息补齐」，不写「重连逻辑正确」。

这份清单是本轮的**验收基准**：收尾时逐条核，`cwl-code-review` 也拿它当 Spec 轴的对照物。任务验收通过、改动提交后删掉。它不进 `docs/workflow/specs/`——那是重流程的产物。

写完先自检四问，有问题当场改，不要留到推进中才发现：

- 有没有写着「待定」「看情况」的条目？改成确定的。
- 「要做」和「验收」之间有没有对不上的？清单里说了要做的，验收里得能验；验收里有的，清单里得先要。
- 范围是不是还装得下一次交付？装着装着发现要拆，就回去判断该不该升级。
- 有没有哪条能被理解成两种意思？挑一种写死。

## 一次做到位

- **接真实路径**：代码落在正式位置，接真实数据和调用方；开发、调试、联调都走项目里真实的那条路。
- **同一套写法**：沿用项目既有的结构、命名、错误处理与依赖方式，写出来的代码和周围代码是一回事。
- **改动成链**：改了签名就把所有调用点一起改完；新增分支就把配套的错误路径一起处理；加了配置就把默认值和文档同步。任务涉及几处就改几处。
- **判断就地做**：需要拍板的地方按现有代码的做法定；影响对外接口、数据形状或别人怎么调用的决定，边说边做，让用户有机会拦下。

**完成判据**：每个函数体都有真实实现，每条路径都接通，收尾时用户可以直接运行或使用它，从它开始继续往下做。

## 为什么可以直接做

代码便宜，等待昂贵：实现写错，改回来是几分钟的事；卡住等人，花掉的是人整段的注意力。

- **可逆的改动自己定**：把结果摆出来，让人事后纠正。
- **产品方向归人**：方向由用户决定，执行由自己推进。
- **问题下一轮修**：发现的问题记下来，别让它拖住当前任务。

## 短板要点名

收尾报告里固定列出三项：架构上不够通用的地方、功能覆盖的缺口、没有穷尽的边界情形。每一项给出具体位置和影响，交给用户决定先补哪个。实现本身的质量照上面的完成判据走。

## 范围变大就升级

推进中触到下面任一条，停手说明情况，回到 `cwl-grill-with-docs`（方向还没想透）或 `cwl-to-plan`（要把工作拆成计划）：

- 实际牵涉的改动远超这个任务。
- 要改对外接口或数据模型。
- 会影响跨模块的行为。
- 需要先定一个设计决定。

遇到不可逆或影响共享状态的操作、缺权限或关键输入时，同样先确认再继续。

## 收尾

验证节奏按上面找到的那份 `PREFERENCES.md`；没有偏好时，默认做完后跑一次最小但有效的检查。

**每条结论都对应本次实际跑过、看过的输出。**

### 通读一遍自己的 diff

用 `git diff HEAD` 看全部改动（已暂存和未暂存），再用 `git status` 确认没有漏看的新文件。核对三件事：

- 「要做」清单上的每一条都落了地。
- 「验收」清单上的每一条都能在本次跑过的输出里找到对应。
- 改动只落在任务需要的地方，调试用的临时代码、探针、占位实现都已清理。

### 报告

简短报告，各一行：

- **做了什么**：一句话说清这次推进了哪条路径。
- **验证**：跑了什么、结果如何。
- **交给你验的**：哪些「验收」条目我在本地证明不了，只能你亲自确认。说清是哪几条、怎么验。
- **假设**：替用户拿的主。
- **短板**：见上一节，逐条点名。
- **最可能出问题的地方**：这次改动里最容易在后续暴露的那一处。

要更清楚的视图（文件树 / 调用树 / 伪代码），或要写成 PR 正文，用 `cwl-pr`。

#### 验证结论只有三种

每条「验证」写的时候，先归到这三种之一：

- **通过**：基线与处理后按预期方向变了，达到你要的结果。给出前后两组输出。
- **没通过**：行为没变、方向相反，或没达到。
- **说不清**：基线无效、测量失败、日志被截断，或环境不同让对比不成立。

「说不清」不降级成「通过」，也不算失败——它指的是这种情况：本地确实没法证明，需要人来看。把它连同原因写进「交给你验的」。

### 评审由你手动发起

按你要看的维度，这里有两个入口：

- 代码标准与 spec 符合度 → `cwl-code-review`（会先取 `docs/workflow/spec-lite/` 里那份清单当 Spec 轴）
- 这次 diff 与整体架构是否匹配 → `cwl-improve-codebase-architecture`

按项目约定不自动提交。

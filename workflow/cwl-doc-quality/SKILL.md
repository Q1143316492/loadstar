# doc-quality

**只治一个毛病：列举了却不展开。**

AI 写的文档最常见的"不通顺"不是用词难，而是**摆出一串东西就往下走**：
一列文件名、一串术语、一份编号清单、一个"七个可用件"——**每一条都没说清是什么、为什么、怎么用**。
读者读到那里**脑子里没多出任何东西**，那一处列举就是**占位**。

## 第 0 步：先确定读者是谁

**"该不该解释"取决于读者**，不是取决于词。所以先确认（或问）这篇文档写给谁看：
例如"写给写过 Unreal 的人"——那么 Unreal 领域的词、项目内的自造词都不算卡住。
**没有读者背景，就只能瞎报**（这正是这类技能最常犯的错）。

## 唯一的检查动作

找到文档里每一处**列举**（项目符号、编号清单、并列短语、表格里成排的短格），逐条问两句话：

1. **这一条展开过吗？**（下文有没有说清它是什么 / 怎么做 / 为什么值得存在）
2. **读者拿这一条能做什么？**（能改一行代码？能避一个坑？能做一个决定？）

**两问都答不上 → 这条是无价值的占位**，二选一：**展开成一句人话**，或**删掉**。

输出格式：`行号 + 原文片段 + 判为占位的原因 + 建议（展开成什么 / 直接删）`。

## 什么不算问题（不要报）

- **读者本行的词**：该不该解释取决于**读者是谁**——所以先确定读者（本文写给谁看），
  只报**读者背景之外**的词，且优先报**外来词与缩写**（`oracle`、`YAGNI`、`idempotent`、`SLA`）。
  例：读者是 UE 开发者时，"虚幻 / GAS / 蓝图 / 关卡"**不算卡住**，不报；版本号写法（v1.5）也不报；
- **风格**：用词含糊（"大概 30 个文件"若属实就是准确表达）、句子长短、有没有连接词、篇幅；
- **术语表之外的新词**（除非它真的让人读不懂，才报，报的时候必须引用原句说明读者会卡在哪一句）；
- **代码标识符、字段名、路径**（`GameFeatureAction`、`tokenUsage`、`templates/`）。

## 两条边界

1. **只审文档自身**：不去仓库核对引用、不验证内容真伪（那是代码评审/事实核查的事）。
2. **本技能没有脚本**：该不该展开是语义判断；模型本来就要通读，正则只会猜关键词。
   （实测代价：写过 140 行扫术语的脚本，为一份文档修两轮误报才收敛——那是迁就文档，不是判质量。）

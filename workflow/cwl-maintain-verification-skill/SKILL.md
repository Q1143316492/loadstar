**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

手册在应用改变的那一刻就开始腐烂。这个技能是它的保养循环。

维护的单位是**功能**，不是每一句话：每个功能文件都要从源码覆盖一遍、再实际驱动一遍，但不必逐条重证。

产物格式与证明标准见 [`../cwl-create-verification-skill/SKILL.md`](../cwl-create-verification-skill/SKILL.md) 与它同目录的 `references/feature-map-format.md`。

## 编辑范围

只改 `docs/workflow/verify/<名字>/` 里的东西：`README.md`、各功能文件、以及它自己的驱动脚本。

**产品代码一行都不动。** 地图描述的行为，应用不再做了——要么是文档漂移（改地图），要么是产品回归（报告，不在地图里糊过去）。

## 一次维护分五步

**0. 定位目标。** 用户给了手册名就用它；没给时读 `docs/workflow/verify/`，只有一个就用那个，多个就问。一份都没有时停下来，指向 `cwl-create-verification-skill`，而不是凭空造一个。

**1. 索引卫生。** 读 `README.md` 的功能索引，glob 同级文件。修掉缺失、多余、重复、指向不存在文件的条目。这一步很轻，不做清单生成。

**2. 源码普查。** 一个功能文件派一个**只读**子智能体，并行发出。每个回答「这个用户可见功能在源码里怎么运作」，标出疑似漂移并给出位置，返回一份简短的实跑配方。子智能体不驱动应用、不改文件。

功能很少时（个位数），主线程顺序读完即可，不必派子智能体。

返回形状：功能摘要 / 源码入口 / 疑似漂移或「无」 / 一份配方。

**3. 对账。** 每个功能文件都有返回结果。合并重叠的配方，落到尽量少的应用状态上。抽查被引用的漂移；没被引用为漂移的干净结论不重证。扫一遍近期改动，找地图上没有的用户可见面——认定「漏了」之前必须先给出具体源码路径。

**4. 实跑。** 源码看着干净也要跑。所有驱动由主线程负责，按手册自己的启动模型：服务与 UI 一个长驻实例串行驱动；短命 CLI 每次驱动开独立会话。

**每个功能至少走一次**，全程守三条不变量，无论中途出什么故障：

- **体检先于驱动。** 首次驱动前体检；会话语义下每次新会话体检；任何一次驱动失败后重新体检。不驱动一个上次行为异常之后没重新体检过的实例。
- **体检看不见的故障就重启。** 进程健康但 UI 卡死时，重置到已知状态或重新拉起，别指望它自己好。
- 已经抓到的证据要活过每一次清理，**清理之后到它被点名的位置去看一眼**，不是假设。
- 一次驱动起的任何东西都不该活过这次驱动的用处。失败迭代的残留要清，不管会话是卡住、已退出、还是共享的（共享实例只清残留，不动实例）。

体检失败若由手册漂移引起，那属于漂移：在编辑范围内修掉，重启被这次修复作废的东西，**只重启这些**，再试一次。功能到不了时，只有在给出具体前置条件（鉴权、授权、系统版本、外部状态）和尝试过的路径之后，才能记作「已核实不可达」；地图漏了那条前置条件，这本身就是漂移。

任何因分诊而产生的驱动修复，交付前都要重新实跑一遍。最后一次驱动之后的收尾——包括这些重证——才算整个运行结束，证据按手册的规定留下。

**5. 分诊。** 用户视角描述错了或漏了 → 文档漂移，改它。行为正常但驱动不起来 → harness 缺口，修它（脚本可执行、调用写在手册正文里）。应用本身坏了 → 产品缺口，记下来给用户，不放进这次改动。

## 结局

每次维护给出三种之一，并说清是哪一种：

- **clean** —— 每个功能都过了源码与实跑覆盖，没有值得交的东西。**不建分支、不开 PR。**
- **changed** —— 一个 PR，里面是被证明过的文档、驱动、地图修正。改过的文件先重读一遍再交。
- **blocked** —— 覆盖没跑完，或者证过的修复不能安全交付。说清被什么挡住。

## 报告

每个功能一行：覆盖到了没有、发现了什么、归到漂移还是回归。最后给出结局，以及这次仍然没覆盖的部分。

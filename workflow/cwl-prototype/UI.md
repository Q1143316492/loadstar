# UI 原型

在同一条路由上生成**几个截然不同的 UI 变体**，用一个浮动底栏切换。用户在浏览器里翻来翻去，挑一个（或从每个里各偷一点），其余扔掉。

问题若关于逻辑 / 状态而非「长什么样」，那是错误分支。用 [LOGIC.md](LOGIC.md)。

## 什么时候是正确形状

- 「这个页面该长什么样？」
- 「在定稿之前，我想看这个仪表盘的几个方案。」
- 「试试设置页的另一种布局。」
- 任何否则用户要在脑子里对着三张模糊草图纠结一天的场合。

## 两种子形态：强烈优先子形态 A

UI 原型**顶在应用其余部分的边上**时好判断得多：真实的头部、真实的侧栏、真实的数据、真实的密度。一条孤零零的一次性路由是真空：每个变体单看都挺好。只要存在一个说得通的既有页面来承载变体，就默认子形态 A。只有原型确实没有就近的家时，才够到子形态 B。

### 子形态 A：挂到既有页面（首选）

路由已经存在。变体渲染在**同一条路由**上，用 `?variant=` URL 查询参数切换。既有的数据获取、参数、鉴权全部照旧，只有渲染被换掉。这是默认选项；除非有具体理由，就选它。

如果原型针对的东西还没有页面、却*天然该住在某个页面里*（仪表盘的新区块、设置页的新卡片、既有流程的新一步），它仍然是子形态 A。把变体挂进宿主页面里。

### 子形态 B：新建页面（最后手段）

只有当被原型的东西确实没有可栖身的既有页面时才用（例如全新的一级界面，或一个没法合理嵌入任何地方的流程）。

按项目已有的路由惯例建一条**一次性路由**。不要发明新的顶层结构。命名要一眼看出是原型（例如路径或文件名里带 `prototype` 字样）。同样用 `?variant=` 模式。

承诺子形态 B 之前先做一次理智检查：真的没有可嵌入的既有页面吗？空路由会藏起有内容的页面会暴露的设计问题。

两种子形态的浮动底栏完全一致。

## 流程

### 1. 写下问题、定好 N

默认 **3 个变体**。超过 5 个就不再「截然不同」、开始变成噪音，所以封顶 5 个。

把计划写一行，放在原型所在处或文件顶部注释：

> 「设置页的三版变体，经 `?variant=` 切换，挂在既有 `/settings` 路由上。」

用户在场与否都能用。

### 2. 生成截然不同的变体

逐个起草。每一版都守住：

- 页面的目的，以及它能拿到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，等等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层级、不同的首要可供性（affordance），而不是只换配色。三个微调过的卡片网格不叫 UI 原型，叫壁纸。如果两稿太像，重做其中一版，明确要求「不许用卡片网格」。

### 3. 接起来

在路由上做一个切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（既有页面）：切换器之上既有的数据获取全部保留；只有渲染的子树随变体变化。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂同样的切换器。

### 4. 构建浮动切换器

屏幕底部居中的小型固定定位栏，三件东西：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体键，若变体导出了名字也一并显示。如 `B (侧栏布局)`。
- **右箭头**：切到下一个变体（循环）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由器，如 Next 的 `router.replace`、React Router 的 `navigate` 等），让变体可分享、刷新不丢。
- 键盘：`←` 和 `→` 方向键也能翻。焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时不要拦截方向键。
- 视觉上与页面明显不同（例如高对比小胶囊、轻阴影），让人一眼知道它不是被评估的设计的一部分。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价判断挡住，别让误合进来的原型把这条栏发给用户。

把切换器做成单个共享组件，两种子形态都能复用。放在项目放共享 UI 的地方。

### 5. 交出去

把 URL（和 `?variant=` 的键）告诉他们。用户有空就会翻。有意思的反馈通常是**「我要 B 的头部配 C 的侧栏」**——那才是他们真正想要的设计。

### 6. 收敛答案并清场

某个变体胜出后，先收敛答案（选了哪版、为什么），再按 [SKILL](SKILL.md) 里的方式收敛原型。把胜者并回真实代码，其余搬到一次性分支、不进主线：

- **子形态 A**：把胜者并进既有页面；把落选变体和切换器从主线删掉。
- **子形态 B**：把胜出的变体提升为真实路由；把一次性路由和切换器从主线删掉。

全部变体是一手来源，所以它们进一次性分支而不是垃圾桶——留在主线的变体组件和切换器烂得快、还会误导下一个读代码的人。

## 反模式

- **只有颜色或文案不同的变体。** 那是微调，不是原型。真正的变体在结构上互不同意。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁了意义。每一版都该有权力扔掉布局。
- **把变体接上真实写操作。** 只读原型就很好。变体需要写时就指向桩：问题是「这该长什么样」，不是「后端通不通」。
- **把原型直接提进生产。** 变体代码是在原型约束下写的（无测试、最小错误处理）。并回时重写规整。

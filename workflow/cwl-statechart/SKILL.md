**先读 `docs/workflow/AGENTS.md`**（若存在）：本项目自己的工作流约定。

图用**读它的人的话**说明系统怎么在状态之间移动。行为对不对，由那个人判断。

## 跑

在仓库之外的临时目录里工作。写一份 TLA+ 规格和它的配置，然后：

```sh
<技能目录>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，用能执行 TypeScript 的运行时启动。`scripts/statechart` 是一个 POSIX shell 脚本，会挑一个运行时。

**本机（Windows）**：

```sh
export TLA2TOOLS=<仓库里的 tla2tools.jar 路径>
export JAVA=<jdk 的 java 路径>
node --disable-warning=ExperimentalWarning <技能目录>/scripts/statechart.ts \
     SPEC.tla --config SPEC.cfg --view SPEC.view.mjs --out out
```

需要 Node 22.18–22.x 或 23.6 以上。设了 `TLA2TOOLS` 和 `JAVA` 就不用 mise，也不联网。

## 写规格

- 每条**读者认可**的规则写成一个 `INVARIANT`。规则可以关于一个界面、一个结果、一个存下来的值、或一条消息。模型里没有对应变量，就加一个变量。**绝不放宽规则让它成立。**
- `Next` 写成各 action 的析取，例如 `YouPressPlay \/ YouPressStop`。不这么写，TLC 会把每一步都命名为 `Next`。
- 没有出口的状态会违反 `NoDeadlock`，即使它是一个正确的终态。当 `INVARIANT` 或 `PROPERTY` 已经占用了那个名字，规则叫 `CHECK_DEADLOCK`。往 `Next` 里加一个只在终态为真、什么都不改的 action，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 挑图

需要判断的活由你做：每个状态和箭头上的词、阶段和它们的颜色、标题、给读者的报告。把你的工作放进一个 view 模块，用 `--view` 传进去。

view 导出 `state(vars)` 来显示读者的话。`state()` 返回值的形状决定图的形式：

- 返回字符串 → 平铺图：`export const state = (v) => (v.paid ? "已付款" : "付款中");`
- 返回数组 → 父子状态：`export const state = (v) => v.main.split(".");`
- 返回对象 → 每个键一个并行区域：`export const state = (v) => ({ 播放: v.playback, 音量: v.volume });`

每个状态用读者看得见、或在意的事来命名，比如「付款中」「租约已持有，写入待定」。标签里不出现变量名。在 `vars` 里，TLA+ 的**序列是一个从 1 开始编号的对象**，所以 `v.pc[1]` 写成 `pc["1"]`；**集合是数组**。

view 还可以导出 `step(action, from, to)`。它拿到 TLC 的 action 名和这一步前后的值，返回箭头上的标签。每个步骤标签都写成读者看到事情发生的样子，比如「你按下播放」「连接失败」。**标签里不出现代码名或 TLA+ 的 action 名。** 在图上终态相同的两个 action 用同一个标签，于是它们共用一条箭头。

当某一步只在某些条件下发生，把条件用方括号写在标签末尾，用读者的话，例如 `你按下播放 [文件加载中]`。在并行区域的图里，命令会自己把其他区域的条件用它们的标签写进箭头，例如 `[离线时]`。你的方括号会取代它，于是一个状态出发的两条箭头可能看起来一样。所以并行区域的图里，不要给别的区域的条件写方括号。当某个标签没显示的值决定了这一步走向哪里，把结果写进标签，例如「名单读取失败」。

view 还可以导出这些：

- `group(vars)` 返回阶段名。每个图节点拿到它所属组的颜色。一个图节点背后的模型状态分属不同组时，这个节点没有颜色。
- `colors` 给每个组名一个颜色类。
- `title` 是一个字符串，显示在图顶部。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都用这些答案。**所以每个函数只能依赖它的参数。**

图不会画停在一个标签里的步骤。读者必须看见这种步骤时，拆开标签。

**目标约 20 条箭头以内**，更密的图读不动。先让 `state()` 返回更粗的标签：把行为相同的值合并成一个标签，省掉读者不需要的细节，比如一个正在进行、返回也不改变任何东西的调用。**保留 bug 路径上的每个状态，保留每个标记。** 合并会把 `breaks` 变成 `mayBreak`，那就藏起了规则在哪里破。**不要合并违反不同规则的两个状态**，读者否则看不出哪条规则在哪里破。图还是太密，就对读者不需要的步骤从 `step()` 返回 `null`，比如每个状态都有的重置，或者箭头重复了别处已经说过的事。藏步骤时守这些规矩：

- 每个图节点都要能从起始状态由箭头到达。
- 模型里有出口的每个图节点，至少留一条出边。
- 一条箭头上的步骤**要么全藏，要么全不藏**。只藏一部分，它的条件就变窄了。
- 交接时说清图藏了哪些步骤。

## 读报告

- 图上违反规则的节点带 `breaks` 类。它背后的模型状态里只有一部分违反时，带 `mayBreak`。Legend 写出每个标记对应的规则。两条规则同时违反时，它把两条写在一个标记上，所以在交接时说清哪个状态违反哪条规则。并行区域的图里，一个节点在**包含它的每一种区域状态组合**都能违反规则时，才拿到标记；某种组合能违反而其中没有任何节点有标记时，这个组合里每个节点都拿到标记。
- TLC 会越过违反规则的状态继续走，所以图上能看到 bug 之后的状态。
- 正因为 TLC 越过 bug，没有状态上限的模型会一直跑。常量取小，或者加 `CONSTRAINT`。
- 用了 `VIEW` 或 `SYMMETRY` 时，TLC 把它视为同一种的状态只算一个，图也就只画一个。箭头可能指向它，而不是这一步真正到达的状态，报告会说明。
- TLC 检查越过 `CONSTRAINT` 或 `ACTION_CONSTRAINT` 的每个状态上的规则，但不探索那个状态，也不检查它是否死锁。TLC 对某条规则的最短路径终止在这样一个状态时，图画出那个状态，报告给出那条路径。边界之外的其他状态图不画，这种状态里的死锁不会显示。`ACTION_CONSTRAINT` 排除的每一步之后，TLC 也检查规则，即使它以另一条路到达下一个状态。某条规则的最短路径以这样一步结束时，图画出这一步。
- 命令按配置原样用一个 worker 检查规则。某条规则违反时，命令移除这条规则再跑 TLC，直到没有规则违反。第一次违反之后，每次运行停在 10 万个不同状态，让大模型不至于跑不完。一次运行到达这个上限或因错误停下时，报告在「Rules not checked」下列出没检查的规则，图也不给它们标记。没检查的规则可能成立也可能违反。要检查它，把违反的规则从配置里拿掉，或者把模型做小。这个上限会加一个模块，改变 TLC 的变量顺序，所以对 `PROPERTY` 来说，TLC 找到的反例可能和没有上限时不同。
- `tlc.out` 是 TLC 按原配置打印的东西。图没有画出某条违反规则的最短路径时，`tlc-RULE.out` 是找到它那次运行打印的东西。TLC 重复第一条警告时，原生 TLC 打印两次，但 `tlc.out` 只显示一次，因为这个命令读取的输出里 TLC 省掉了第二份。这只在 Java 用 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告是它建议你加这个 flag，那条只打印一次。

## 把图给用户看

把 `chart.mmd` 作为 `mermaid` 代码块给用户看。图的预算是 500 个状态，按原配置由 TLC 计数。超过之后，图只画通往违反规则的那些路径；没有规则违反时，命令不写 `chart.mmd`。它仍然检查每条规则，报告给出状态数和每条 bug 路径。想看完整的图，把模型做小。

渲染用 Pele。用户要图片、或者图大到没法当文本读时，按 [`references/render.md`](references/render.md) 走。用户没要求时不用别的渲染器。

## 交接

把每张图和它的 Mermaid 文本交给要做决定的人。每条 bug 加一行：规则、读者对这条规则的句子、按报告编号的路径。说清模型省掉了什么。给出重新生成文件的命令，用一个新 `--out` 目录。

模型描述的是代码时，把每条 bug 路径在真实代码上重放成测试或 live repro，一个 action 一步。**bug 复现不出来时，先认为模型错了，直到你证明它不是。**

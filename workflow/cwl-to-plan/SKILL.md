本技能拿当前对话上下文和对代码库的理解，产出**计划**：一份 spec，加一组拆好的 ticket，全部写入本地文件。

**不做访谈**：只综合你已知的内容——把想法问清楚是 `/cwl-grill-with-docs` 的活。流程里只有两处停下来与用户确认：接缝（第 1 步末）与拆解（第 4 步）。那不是访谈，是让用户批准你的分解。

产物与目录约定：

```
docs/specs/<feature-slug>/
├── spec.md              ← 第 2 步的产物
└── tickets/
    ├── 01-<slug>.md     ← 第 5 步的产物（每 ticket 一文件）
    └── 02-<slug>.md
```

`<feature-slug>` 用简短的连字符短名（如 `user-export`）；目录不存在就创建。

**规划边界**：本技能只产出规划产物。写完就停下——不写产品代码、不提交、不进入实现。实现由用户在读完计划后另起 `/cwl-implement`。

**产出的先后与默认**

顺序固定：**先 spec，后 ticket**。spec 是这一轮的契约；ticket 只能从 spec 推出来，不能直接从对话里推。`spec.md` 落盘之后，才进第 3 步切票。

默认一次产完：写完 spec 不停，接着切票、确认、落盘。只有用户**明确**说了「先只要 spec」「spec 先给我看看」时，才在第 2 步末尾停下，交付 spec，等用户发话再拆。

两种单独入口：

- 用户传入一份已有 spec 的路径：跳过第 2 步，从第 3 步起照常（接缝若 spec 里已定，就不必再确认）。
- 用户只要 spec：按上面的例外处理，做完第 2 步停下。

## 流程

### 1. 探索代码库 + 勾接缝

从对话上下文中已有的内容开始工作；用户作为参数传了引用（spec 路径或功能名）的，先把它取来读完。探索仓库，理解代码库的当前状态，如果你还没做过的话。整份计划都要使用项目领域词汇表的术语，并尊重你正在触及的区域中的任何 ADR。

用户给的是**地图**（`docs/maps/<地图名>/` 的路径，或地图名）时，先读 `map.md`，再读「已定决策」指向的票全文。那些是**已定决策**：不重新推、不重新盘问，把它们收拢进 spec 的「实现决策」一节；地图此后只作索引，不当施工清单。地图还没清（前沿仍有待办的票）时，先停下点名还差哪几张——不要带着未决问题写计划。

寻找把代码预重构（prefactor）的机会，让实现更容易。「先让改动变简单，再做那个简单的改动。」

勾勒出你将要测试这个功能的那些接缝。已有的接缝应优先于新建接缝。使用尽可能高的接缝。如果需要新接缝，就在你能做到的最高点提出它们。整个代码库里的接缝越少越好——理想数量是一个。

与用户确认这些接缝符合他们的预期。这份接缝清单同时约束第 2 步的测试决策和第 3 步的切片。

### 2. 写 spec

用下面的模板写 spec，写入 `docs/specs/<feature-slug>/spec.md`。

<spec-template>

## 问题陈述

用户所面临的问题，从用户的视角描述。

## 解决方案

该问题的解决方案，从用户的视角描述。

## 用户故事

一份**长长的**、带编号的用户故事列表。每个用户故事都应当是这种格式：

1. 作为 <角色>，我想要 <功能>，以便 <好处>

<user-story-example>
1. 作为一名手机银行客户，我想查看我账户的余额，以便更明智地做出消费决策
</user-story-example>

这份用户故事列表应当极其详尽，覆盖该功能的方方面面。

## 实现决策

一份已做出的实现决策的列表。可以包括：

- 将要构建/修改的模块
- 那些模块中将要被修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体的交互

**不要**包含具体文件路径或代码片段。它们可能很快就会过时。

例外：如果某个原型产出了一段代码片段，它比散文更精确地编码了某项决策（状态机、reducer、schema、类型形状），就把它内联到相关决策里，并简要注明它来自原型。裁剪到承载决策的部分，不要工作 demo，只要关键片段。

## 测试决策

一份已做出的测试决策的列表。包括：

- 对什么算好测试的描述（只测试外部行为，不测实现细节）
- 哪些模块会被测试
- 测试的先例（也就是代码库中类似类型的测试）

## 超出范围

对这份 spec 中超出范围之事的描述。

## 补充说明

关于该功能的任何补充说明。

</spec-template>

### 3. 起草垂直切片

把工作拆成**曳光弹（tracer bullet）** ticket。

<vertical-slice-rules>

- 每个切片都切出一条穿过每一层（schema、API、UI、测试）的狭窄但**完整**的路径：是垂直的，而**不是**某一层的水平切片
- 一个完成的切片自身就是可演示或可验证的
- 每个切片的大小以能放进一个全新的上下文窗口为准
- 任何预重构都应先做完

</vertical-slice-rules>

切票**只从 spec 推**：每张 ticket 都要能在 spec 里找到依据（接缝、实现决策、测试决策）。切的过程中**不做新决定**——碰到 spec 没覆盖的决定，先回写 spec，再回来继续切。

切完做一次「遮住对话」检查：假装只看得到 `spec.md`，逐张问这张票还成立吗？不成立的那张，依据只存在于对话里，把它补进 spec。

给每个 ticket 标出它的**阻塞边（blocking edges）**：在它开始之前必须完成的其他 ticket。没有阻塞者的 ticket 可以立刻开始。

**大范围重构是垂直切片的例外。**一次**大范围重构（wide refactor）**是一次机械改动（重命名一列、给一个共享符号改类型），它的**爆炸半径（blast radius）**扇及整个代码库，于是一次编辑就同时弄坏成千上万个调用点，任何垂直切片都无法以绿色落地。不要硬把它塞进一颗曳光弹，而要把它排成**扩展–收缩（expand–contract）**。先扩展：在旧形式旁边加上新形式，这样什么都不会坏。然后按爆炸半径分批迁移调用点（按 package、按目录），每批自成一个 ticket，阻塞于那次扩展；由于旧形式仍然存在，批次之间 CI 保持绿色。最后收缩：在没有任何调用者残留之后删除旧形式，这个动作放在一个 ticket 里，阻塞于每一个迁移批次。当连这些批次都无法各自保持绿色时，保留这个顺序，但让它们共用一个集成分支，并且所有这些批次都阻塞一个最终的「集成并验证」ticket；只有在那里才承诺绿色。

### 4. 向用户确认拆解

把提议的拆解作为编号列表呈现出来。对每个 ticket，展示：

- **标题**：简短描述性名称
- **阻塞于**：哪些其他 ticket（如果有）必须先完成
- **交付什么**：这个 ticket 让什么端到端行为得以工作

问用户：

- 这个粒度感觉对吗？（太粗 / 太细）
- 阻塞边正确吗：每个 ticket 是否只依赖真正卡住它的那些 ticket？
- 有没有 ticket 应该合并或进一步拆分？

迭代直到用户批准这个拆解。

### 5. 写出 ticket 文件

把批准的 ticket 逐个写入 `docs/specs/<feature-slug>/tickets/<NN>-<slug>.md`，从 `01` 开始按依赖顺序编号（阻塞者在前）。每个文件的「阻塞于」列出它所依赖的编号/标题。用下面的模板：每个 ticket 一个文件，绝不合并成一个文件。

按**前沿（frontier）**推进：任何阻塞者都已完成的 ticket 都可以开始。对于一条纯线性的链条，那就是从上到下。

<ticket-template>

# <NN>：<ticket 标题>

**要构建什么：** 这个 ticket 让什么端到端行为得以工作，从用户的视角描述，而不是一层层的实现清单。

**阻塞于：** 卡住这个 ticket 的那些 ticket 的编号/标题，或者「无（可立即开始）」。

- [ ] 验收标准 1
- [ ] 验收标准 2

</ticket-template>

写 ticket 时避免具体文件路径或代码片段：它们很快就过时。例外：如果某个原型产出了一段代码片段，它比散文更精确地编码了某项决策（状态机、reducer、schema、类型形状），就把它内联，并简要注明它来自原型。裁剪到承载决策的部分，不要工作 demo，只要关键片段。

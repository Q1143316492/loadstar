# 原型

原型是**回答一个问题的用完即弃的代码**。问题决定它的形状。

## 选分支

判明在回答哪个问题——用用户的提示、周围的代码，或者（用户在的话）直接问：

- **「这个逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个单文件的、可分享的 HTML（自由操作按钮 + 分页的引导式走查），把状态机推过那些在纸面上难以推理的情形，而且非开发者也玩得动。
- **「这个应该长什么样？」** → [UI.md](UI.md)。在同一条路由上生成几个截然不同的 UI 变体，用一个 URL 查询参数和浮动底栏切换。

两个分支产出的东西很不一样，分支选错整个原型就白做了。问题真正含糊、又联系不上用户时，默认选更贴近周围代码的那个分支（后端模块 → 逻辑；页面或组件 → UI），并把这条假设写在原型顶部。

## 两个分支都适用的规则

1. **从第一天起就是用完即弃的，并且明确标记。** 原型代码放在它将来真正被用到的位置附近（它为之做原型的模块或页面旁边），让上下文一目了然；但命名要让随便谁一眼看出这是原型、不是生产代码。用完即弃的 UI 路由，遵守项目已有的路由惯例；不要发明新的顶层结构。
2. **启动毫无门槛。** UI 原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是用户双击就能开的单个 HTML 文件。总之，启动不需要动脑。
3. **默认不做持久化。** 状态放在内存里。持久化是原型要*检验*的东西，不是它该依赖的东西。问题确实涉及数据库时，用一个草稿库或本地文件，并且命名清楚地写着「PROTOTYPE，随时可删」。
4. **跳过打磨。** 不写测试，不做让原型*跑不起来*之外的多余错误处理，不做抽象。要点是快速学到点东西。
5. **暴露状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到什么变了。
6. **完成后收敛。** 把验证过的决策并回真实代码，然后把原型本身作为**一手来源**留存：提交到一个用完即弃的分支（离开主线），并在对应 ticket 里留一条指向该分支的**上下文指针**。答案（结论，以及它回答的那个问题）也一并留在 ticket 或提交里。主线只保留验证过的决策。
